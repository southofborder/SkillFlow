## 对后续模型反馈和修复的检查标准

1. 真正命中应明确指出“archive 失败返回前缺少状态追加”，并指向当前失败终态的完整操作清单或现存 return 之前。仅说“缺约束”“改标题”不构成正确修复目标。
2. 模型可以把它报告为遗漏，也可以同时指出声明—操作冲突；若两个条目指向这一相同注入，按一个受控缺陷计数。
3. 修复应恢复真实的追加操作与先于失败 return 的指令次序；状态格式未规定，不能强制额外加入错误正文、工具名、时间戳或密钥。
4. 修复不得吞掉、替换或包装 archive 错误，不得再次调用 archive，不得新增等待，不得删除其他成功终态的状态追加。
5. 新图生成后，应重新核对全部 9 条原文要求和结果定义引用；当前旧图的 `block_014` 或 `ir_028` 只描述种子图，不是修复图必须沿用的 ID。

### 真实缺陷和定向建议

`finding_9` 正确指出：全局约束要求失败返回前追加状态，`block_014` 的名称虽然仍写 Append，但实际完整操作清单只有 return，因此真实追加步骤缺失。模型选择 internal_conflict，并在理由里明确说明同时遗漏了源文失败路径要求。助手认为该分类和解释都命中了真实注入缺陷。

建议引用 `fact:/blocks/13/instructions` 和 `fact:/blocks/13/instructions/0`，程序分别定位到 `/blocks/block_014/instructions` 与 `/blocks/block_014/instructions/0`。两者都属于当前实际图；后一个确实是现存 `ir_028 return(result_012)`，没有引用已经删除的 `ir_027` 作为当前操作。建议是在该 return 前补充 append，并使用 status.txt 与失败状态，将 `"failure"` 明确写作示例，没有无依据地指定更复杂格式。

因此，**真实遗漏已命中，反馈位置和修改方向正确**。没有发现额外的明确语义误报；其余 represented 业务判断与独立种子审查一致。

### 必须保留的未决：把 dispatch 当作开放业务操作

`finding_13` 认为源文没有独立的 dispatch 业务步骤，而受控文字没有说明 dispatch 是否只是控制连接，因此把 10 个 dispatch 操作的业务含义标为 unknown，并没有给出删除或改写建议。

这不是 c03 新增的源文缺陷。既有 IR 和固定提取契约实际上把 dispatch 规定为有出边基本块的终结控制角色；它不是任意开放业务操作。与此同时，本次 auditor 的固定表示边界没有明确传达 dispatch/return 这两个固定控制角色例外，实际受控操作标签又笼统使用“开放操作名”。因此，本条反映出**模型对表示层的误读，以及核对输入对固定控制角色说明不足造成的可避免未决**。不能机械地把它记为真实源文遗漏或新增操作，也不能在报告中删掉它或将 unknown 改成 represented。

这项诊断是助手结合现有 IR 契约形成的解释；程序当前没有自动纠正该判断。后续若完善表示说明，应该清楚区分固定控制角色和开放业务操作，而不是要求重新提取时删掉合法 dispatch。本轮源代码、Prompt 和已接受响应继续保持不变，不为获得通过结论补跑。
