# 001 / 010 未决及 revise 的离线复核

复核日期：2026-09-17。读取 `full-pipeline-20260917` 已保存源文、实际 CFG、受控回述与核对结果；没有调用 API、续跑实验或修改历史判断。本文件是助手复核，不是模型实测改善结果。

## 001：IR 控制定义没有告诉核对器，形成可避免的未决

原核对记录：`cases/001/feedback/rounds/r000/audit.json` 的 `finding_8`，是该例唯一 `unknown`。

核对器说源文没有要求 dispatch / return，受控文本没有定义它们的效果，所以无法判断是否新增业务动作。实际 CFG 中这些操作处于块尾，前四个块使用 dispatch 连接后继，最后一个 return 结束流程。现有 IR 契约本来就规定了这两个控制终结操作：见 `src/skill_ir/extraction/prompt.py` 的固定控制角色和终结操作说明，以及 `ir/basic_block.py` / `ir/validation.py` 的结构规则。

这不是网络故障，也不是发现了遗漏业务步骤。问题在于核对提示词只说开放操作名按文字解释，却没把两个固定控制操作的例外传给核对器。新增通用说明可以让后续调用按已有契约判断。仍需检查 return 的值和 dispatch 的条件、出边；不能直接把所有此类记录判保留。未运行新模型，旧 `unknown` 保持原样。

## 010：一次实际搜索响应的身份没有被明确保留下来

原核对记录：`cases/010/feedback/rounds/r000/audit.json` 的 `finding_11`，是该例唯一 `unknown`。

源文 `references/workflow.md`：第 7 行要求 `index.search exactly once`，第 21 行写该响应的 total，第 23 行原样返回该响应的 items。CFG 的四条互斥分支分别产生 `result_006`、`result_007`、`result_008`、`result_009`。随后 `block_007 / ir_012 / extract_search_total_and_items` 把这四个不同响应全部列为输入，输出 total 与 items；该操作的 constraints 为 `[]`、metadata 为 `{}`，未记录按已执行分支选择响应的关系。

因此它不是 001 那种补上固定字段解释就能解决的问题。分支互斥只说明不会同时选中四次搜索，不能让四个输入自动获得 phi 或“只取当前分支结果”的语义。结构良序性只检查定义和连接等条件，并不证明所有路径上的输入同时可用；本次也没有把结构规则收紧成那种保证。

助手判断：这里有可定位的**结果身份表示缺口**，应反馈到 `block_007` 的提取操作及其输入。可用现有 IR 完整表达的修复是：将取 total/items、写文件和返回留在各自搜索分支内，各分支只引用自己的响应；或者明确记录有源文依据的选择关系。不要新增源文没有的搜索、业务数据聚合或数据处理，也不要只加一句约束就宣称执行选择已完成。现有 IR 没有 `conditional_input` 类型或内建 phi，建议不能要求模型编造这些字段。

新增提示词明确区分：能指出缺失的必需绑定关系时报告遗漏/错转并给出目标；如果源文与操作文字本身仍无法裁决，保留 `unknown`。程序没有将此例强制改为某个判定，没有按案例编号写规则，也没有重写旧结果。

## revise：发现明确差异，进入下一轮完整提取

`revise` 是反馈循环本轮的决策，表示存在 omitted / mistranslated / unsupported_addition / internal_conflict 等明确差异且尚有修复额度。它不是网络错误，不是失败的 HTTP 状态，也不等于最终失败。下一步会基于本轮差异重新提取完整 CFG，再完整核对；不能直接修改图字段后宣布通过。

- **007，第 0 轮**：源文说“参数描述不要求预先校验或规范化”，图中一条操作约束变成“禁止校验或规范化”。这是义务强度增强，值得修复。另有 presence flags 被列入工具 inputs 但未明确它们是控制操作数还是业务参数的未决。
- **007，第 1 轮**：核对器认为可选参数缺失分支绕过取值，却在同一工具调用 inputs 中继续列出对应 result，与“缺失时省略”声明不一致。这是需要明确条件与参数绑定的表示问题；建议不能生成不存在的条件输入字段。
- **009，第 0 轮**：同 010，提取 total 和 items 时同时列入四个分支响应，缺少实际响应选择关系，触发重新提取。
- **009，第 1 轮**：也有可选参数缺失时的输入绑定问题；另外两条不能照单全收。一是把为实施源文条件而做的存在性检查，疑为参数值合法性校验；二是把本地 `count.txt` 的 `external_resource` 类型当成远端资源，误报与 local 冲突。

`external_resource` 的定义包括文件、工具、API、服务，是相对图内 result 的资源标识，并不表示网络位置。本地文件用这个类型合法，没有 `local_resource` 这一 IR 操作数枚举。已增加通用定义，避免后续模型要求不存在的新类型。存在性检查仍需确认是否改变值、拒绝请求或增加了源文没有的条件，不能一律豁免。
