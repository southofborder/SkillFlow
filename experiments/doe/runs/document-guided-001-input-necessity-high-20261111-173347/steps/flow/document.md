## Conditional notification flow

1. **Entry and input.** The `conditional-notification` workflow reads the user-provided `events.json`. Each record supplies `recipient`, `summary`, `record_id`, `value`, `urgent`, `opted_out`, and `access_token`. The excerpt leaves imports, a callable signature, and context keys unspecified. (`skill/SKILL.md:1-8`)
2. **Traversal and selection.** At the loop header, test whether the collection has another member. If it does, obtain the current record and test `opted_out`. If it is `true`, skip the record. Otherwise, select the record if `urgent` is `true`. If urgency does not select it, select it only when `value >= 100`. After a send or a skip, return to the loop header. When the collection is exhausted, proceed to the count write. (`skill/SKILL.md:8-10`, `skill/SKILL.md:13`, `skill/SKILL.md:16`)
3. **Delivery.** Call `notify.send` once per selected record. Set `recipient` to that record’s `recipient` and `body` directly to the same record’s original `summary`. Keep `access_token` out of all recipient-bound data throughout the workflow. The body uses the supplied field value directly, without summary generation, rewriting, or format conversion. (`skill/SKILL.md:11-15`)
4. **Storage and gaps.** After processing, write the number of processed records to local `count.txt`. Model the write as replacement with no public result. The excerpt leaves the counting rule, send failure behavior, and any notification return or consumer unspecified. It supplies no later read of `count.txt` or association between a saved file and a separate analysis or summarization step. (`skill/SKILL.md:8-16`)
