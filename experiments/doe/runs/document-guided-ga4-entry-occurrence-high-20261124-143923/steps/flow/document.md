**Initialization and shared state.** Importing settings invokes dotenv configuration for the current working directory. Each `getSettings()` obtains current environment values, converts escaped private-key newlines, defaults the date range to `30d`, and derives the results directory from the current working directory. Validation requires property ID, email and private key, including for Search Console and indexing; it does not require a site URL. Each client getter first returns its existing singleton if present; otherwise validation failure throws, while success creates and stores a new handle using the settings acquired then. GA4 selects `BetaAnalyticsDataClient` from `@google-analytics/data`; Search Console selects `searchconsole` from `@googleapis/searchconsole`, version `v1`; indexing selects `indexing` from `@googleapis/indexing`, version `v3`. The latter two obtain GoogleAuth from `googleapis` with webmaster-readonly and indexing scopes. Cached handles retain their creation provenance, while property/site getters acquire current settings separately. `resetClient()` clears all three bindings. (`skill/scripts/src/config/settings.ts:5-9,40-74`; `skill/scripts/src/core/client.ts:6-15,23-133`)

**Report acquisition and independent helpers.** `runReport(options)` receives required dimensions and metrics, optional date range, filters, ordering, limit and saving. It obtains the client/property and sends mapped dimensions, mapped metrics, one parsed range and a limit only when that limit is truthy. Although accepted and documented, `filters` and `orderBy` are not included in the request. The first response returned by the Google client is the acquired report version; when saving is enabled, that same response is saved before being returned. The operation is dimensions joined by underscores, or `custom`; extra information is the original date-range string only. (`skill/scripts/src/api/reports.ts:20-28,77-109`; `skill/references/api-reference.md:31-45`)

All following helpers pass their own `dateRange` unchanged into `runReport`, with saving left at its default `true`:

| Public helper | Actual dimensions → metrics |
|---|---|
| `getPageViews(dateRange?)` | pagePath, pageTitle → screenPageViews, activeUsers, averageSessionDuration |
| `getTrafficSources(dateRange?)` | sessionSource, sessionMedium, sessionCampaignName → sessions, activeUsers, newUsers, bounceRate |
| `getUserDemographics(dateRange?)` | country, deviceCategory, browser → activeUsers, sessions, newUsers |
| `getEventCounts(dateRange?)` | eventName → eventCount, eventCountPerUser, activeUsers |
| `getConversions(dateRange?)` | eventName, sessionSource → conversions, totalRevenue |
| `getEcommerceRevenue(dateRange?)` | date, transactionId → totalRevenue, ecommercePurchases, averagePurchaseRevenue |

These are separate acquisition capabilities, even where an orchestrator does not use them. (`skill/scripts/src/api/reports.ts:114-175`)

For GA4, `parseDateRange(range)` substitutes the configured default when the operand is falsy, returns an object unchanged, translates an `Nd` string into `NdaysAgo`–`today`, and otherwise returns `30daysAgo`–`today`. Bulk lookup implements its own equivalent parser. Search Console’s exported parser has the same default/object branches but converts shorthand into calendar date strings using runtime dates; unsupported strings fall back to 30 days. Thus an explicit Search Console range object is passed through without converting GA4-relative values. (`skill/scripts/src/api/reports.ts:47-72`; `skill/scripts/src/api/bulk-lookup.ts:103-128`; `skill/scripts/src/api/searchConsole.ts:51-84`)

GA4 orchestrators import their report producers from `./api/reports.js`; Search Console orchestrators use the separately selected Search Console imports. (`skill/scripts/src/index.ts:26-46,55-295`)

`compareDateRanges(range1, range2, dimensions?, metrics?)` defaults dimensions to date and metrics to activeUsers, sessions, screenPageViews. It first requests `range1` with saving disabled, then independently requests `range2` with saving disabled. The returned comparison pairs `period1.dateRange = range1` with the first response and `period2.dateRange = range2` with the second; only this comparison is saved under reports / date_comparison. No delta calculation is implemented. (`skill/scripts/src/index.ts:171-204`)

**Other acquisition boundaries.**

- Realtime functions each accept `save = true`, call `runRealtimeReport` with the current property, optionally save the acquired response, and return it: active users uses unifiedScreenName → activeUsers; events uses eventName → eventCount; pages uses unifiedScreenName → screenPageViews; sources uses firstUserSource, firstUserMedium → activeUsers. Their operations are respectively active_users, events, pages and sources under realtime. (`skill/scripts/src/api/realtime.ts:24-99`)
- Metadata functions each accept `save = true` and request the current property’s `/metadata`. `getAvailableDimensions` returns/saves a new dimensions-only object, defaulting its collection to empty; `getAvailableMetrics` does the analogous metrics projection; `getPropertyMetadata` returns/saves the full acquired response. Operations are metadata / dimensions, metrics and full. `getAvailableFields()` calls the full producer with no arguments and returns that response after logging collection counts. (`skill/scripts/src/api/metadata.ts:38-95`; `skill/scripts/src/index.ts:355-362`)
- `querySearchAnalytics(options)` obtains current Search Console client/site and parsed range, then sends start/end dates, dimensions, row limit and start row. Defaults are query, 1000, 0 and saving enabled. It returns `response.data`, saving that same version under searchconsole with the joined dimensions, or query, and the original string range when supplied. Helpers forward their range: top queries uses query/100 rows; top pages page/100; device device/1000; country country/50; appearance searchAppearance/1000. (`skill/scripts/src/api/searchConsole.ts:89-175`)
- `getMetricsForUrls(urls, options = {})` traverses the supplied paths to trim whitespace and add missing leading slashes, preserving trailing slashes. Empty normalized input returns a new empty report without client acquisition or saving. Otherwise it builds a case-insensitive pagePath list filter and requests pagePath/pageTitle with the parsed range and supplied metrics, defaulting to screenPageViews, activeUsers, averageSessionDuration, bounceRate, engagementRate. The acquired first report response is optionally saved as reports / bulk_url_lookup, with original string range or `custom`, then returned. Independently callable `normalizeUrls(urls)` returns normalized paths; `buildUrlFilter(urls)` returns null for empty input or a filter containing the supplied paths. (`skill/scripts/src/api/bulk-lookup.ts:46-98,149-192`)

**Indexing loops and distinct outcomes.** Single-URL notification functions receive `url` and `options = {}`. `requestIndexing` publishes URL_UPDATED; `removeFromIndex` publishes URL_DELETED. Each constructs a result from returned notification metadata, falling back to the supplied URL and current timestamp, optionally saves it, then returns it. `inspectUrl(url, options = {})` instead sends the supplied inspection URL and current site URL to Search Console, then constructs a projected inspection result: missing index verdict becomes NEUTRAL, coverage becomes Unknown, and optional mobile/rich-result objects are included only when their response sections exist. These results save under indexing / request_indexing, remove_from_index or url_inspection. (`skill/scripts/src/api/indexing.ts:57-80,114-193`)

For each following URL traversal, the loop header tests `has_member` on the actual `urls` collection; the true branch obtains the next URL, processes it and returns to the header, while the false branch proceeds to the final save/return:

| Entry | Per-member call, outcome and receiving collection |
|---|---|
| `requestIndexingBatch(urls, options = {})` | Calls `requestIndexing(current URL, {save:false})`, appending each notification result. An uncaught failure stops traversal; on normal exit, saves batch_indexing only when `options.save` defaults/evaluates true and returns the array. |
| `reindexUrls(urls)` | Calls the same producer with saving disabled. Success appends submitted status plus returned notification fields; the returned result’s URL can replace the initially supplied URL. A caught exception instead appends the input URL, failed status and its stringified error, then traversal continues. Always attempts final reindex_batch save. |
| `checkIndexStatus(urls)` | Calls `inspectUrl(current URL, {save:false})`. Success appends the input URL, whether returned verdict equals PASS, and only returned indexStatus. A caught exception appends that URL, indexed false and a stringified-error status. Continues and attempts final index_status_check save. |

The two high-level loops return their collected arrays after saving; their caught exceptions are distinct from successful API responses. (`skill/scripts/src/api/indexing.ts:89-105`; `skill/scripts/src/index.ts:301-346`)

**Persistence, reading and summarization.** Every producer above sends its actual response, projection or aggregate to `saveResult(data, category, operation, extraInfo?)`. Storage acquires current settings, conditionally creates the category directory, builds a second-resolution local timestamp filename with sanitized operation/extra text, and writes a JSON wrapper containing metadata and that data version. The write replaces its target; identical generated paths can collide. `saveResult` returns the path, but the analysis producers discard it and return their data instead. Storage metadata records current property ID, including for non-GA4 categories; it establishes no additional acquisition provenance. (`skill/scripts/src/core/storage.ts:12-26,31-95`)

`listResults(category, limit?)` returns empty when the directory is absent; otherwise it selects JSON paths, sorts descending by filename and conditionally slices when a limit is supplied. `loadResult(filepath)` separately acquires file content and parses it, returning null for absence or caught read/parse failure. `getLatestResult(category, operation?)` consumes listed paths, optionally filters by a sanitized operation substring, then loads only the first remaining path or returns null. No schema validation or exact operation equality is enforced. (`skill/scripts/src/core/storage.ts:103-171`)

The Skill prescribes **analyze → auto-save → read saved JSON → create a Markdown summary with tables, trends and recommendations**. That obligation remains stated alongside implementation exceptions: optional saving, the empty bulk return, parsing/storage utilities and help output do not all make API calls or save results. No supplied implementation automatically reads analysis output or writes a Markdown summary. The Skill’s example explicitly connects `listResults('reports', 10)` to `loadResult(files[0])`, but its separate `getLatestResult('reports', 'site_overview')` does not prove association with a particular invocation. No actual invocation, saved JSON or summary is supplied, so specific file ownership and analysis-to-summary association remain unresolved. (`skill/SKILL.md:53-64,129-142`; `skill/scripts/src/api/bulk-lookup.ts:158-164`; `skill/scripts/src/core/storage.ts:103-171`)

Other documented relationships remain limited: keyword analysis acquires a device-only report, not query-by-device rows; SEO page analysis acquires separate page and country reports without joining them. The reference describes top pages by impressions, while the Skill/help describe clicks; the implementation supplies no explicit sorting parameter to resolve that conflict.
