1. **Skill scope and setup.** The Skill describes Google PSE searches for live information, documentation or research when built-in `web_search` is unavailable. Setup requires an enabled Custom Search API, an API key and a search-engine CX ID, with credentials stored in a workspace `.env` file (`skill/SKILL.md:3-19`). Its example invokes `skills/google-search/scripts/search.py` with inline environment credentials and the query “OpenClaw documentation” (`skill/SKILL.md:24-28`). These are documented requirements and an example; the script does not enforce the availability condition.

2. **Independent callable entry point.** `google_search(query, api_key, cse_id, num_results=5)` accepts its credentials directly. It sends a GET request to Google’s Custom Search endpoint, pairing `query` with `q`, `api_key` with `key`, `cse_id` with `cx`, and `num_results` with `num`. The returned HTTP response is consumed first by the status check, then by JSON decoding; the decoded API content is returned to the caller. A request failure, status-check failure or decoding failure prevents that normal return; this function has no local exception handler (`skill/scripts/search.py:6-16`). The acquired content comes from Google’s response, not solely from the request parameters.

3. **CLI entry point and order.** Under the main-module guard, fewer than two command-line arguments prints usage and exits with status 1. Otherwise, the query comes from `sys.argv[1]`; the result count is the integer conversion of `sys.argv[2]` when present, or 5. Next, the script reads `GOOGLE_API_KEY` and `GOOGLE_CSE_ID` from the process environment. If either value is falsey, it prints the credential error and exits with status 1, without requesting Google (`skill/scripts/search.py:18-32`). Integer conversion occurs before credential acquisition and outside the later exception handler, so a conversion failure is uncaught there (`skill/scripts/search.py:24-34`).

4. **Call, returned versions and recipients.** After those checks, the CLI calls `google_search` with its actual query, acquired API key, acquired CSE ID and selected count. The function’s decoded return becomes the CLI’s `results`; `json.dumps` consumes that version with indentation 2, and `print` sends the serialized text to standard output. Exceptions raised within this protected sequence are caught as `e`; their string representation supplies a separate error message, followed by exit status 1. Thus a caught failure may occur during acquisition or after a response has already arrived; it does not produce a successful `results` value (`skill/scripts/search.py:34-39`).

5. **Dependencies, state and local gaps.** The script imports `sys`, `json`, `requests` and `os`; HTTP acquisition uses `requests`, serialization uses `json`, and environment acquisition uses `os` (`skill/scripts/search.py:1-4,14,27-28,36`). No supplied code loads `.env`, so the documented file-to-process-environment relationship remains unresolved. No environment mutation, saved search results, later result-file read, analysis or summarization is shown. Consequently, no saved-file ownership or downstream consumer association is established. The Skill’s workflow contains only an ellipsis, and its example path and the CLI’s usage filename differ from the supplied script path; those relationships remain unverified (`skill/SKILL.md:21-28`; `skill/scripts/search.py:20`).
