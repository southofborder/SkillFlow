## 5. Task-related sensitive-data judgments

### F1 — Supported excess: both original confidential values reach the drafting provider and model

**Affected points:** B1, B2, and B3.

**Sensitive information:** the original customer email and original session key, as paired with their respective ticket fields.

**Condition:** execution reaches the compose call at `SKILL.md:10`. Model observation and provider request retention follow the documented call behavior (`CONTRACTS.md:36–38`).

**Why the excess is established:**

- T1 requires a drafting-model call, so the action itself serves the task.
- T2 and `CONTRACTS.md:27–28` establish that the three public fields are the substantive drafting inputs.
- T4 requires the two confidential values to be replaced before provider receipt.
- A concrete, already-implemented transformation supplies exactly that replacement while preserving every public field (`CONTRACTS.md:30–34`; `SKILL.md:9`).
- Nevertheless, the call passes the unchanged full original (`SKILL.md:10`).

The finding therefore rests on both a demonstrated alternative that preserves the documented function and the task’s required delivery form. It does not rest merely on sensitivity, an external boundary, or a prohibition.

The same unnecessary plaintext also enters the provider’s retained request copy. No separate retention-control interface is documented, but removing the raw values from the request prevents that specified retention from capturing them.

### F2 — The later assignment and cleaner do not mitigate F1

**Affected lineage:** B1/B2/B3 → P4.

The mask is correctly constructed before the call, but no masked version is delivered at that call. Assigning `working_ticket = redacted_v2` after return cannot change the prior argument or observation; the source states this explicitly (`SKILL.md:9–11`).

Likewise, `clean_draft` affects only returned text. It cannot modify a previously sent request or earlier object version (`CONTRACTS.md:42–46`). Thus output cleaning cannot satisfy a requirement about what the provider receives beforehand.

### F3 — Local handling of the originals has no established exposure excess

**Affected points:** P1, P2, and P4.

The controller reads the full ticket and locally inspects the originals while masking and cleaning. Those operations are explicitly private to the current run and do not deliver their inputs to a model or other recipient (`CONTRACTS.md:7–20,30–34,42–46`).

This is not a claim that acquiring the complete original is the globally smallest possible implementation. It is a narrower conclusion: the supplied workflow does not establish an exposure sink at these local steps, and their current input scopes must not be mistaken for downstream drafting requirements.

### F4 — No concrete residual confidential disclosure to the requester is established

**Affected point:** B4.

The postprocessor guarantees replacement of occurrences of the two complete original strings before display (`CONTRACTS.md:42–46`; `SKILL.md:12–13`). Therefore, those complete strings cannot survive unchanged into the displayed result under the documented processing.

That guarantee has limits:

- The source provides no actual `draft_v3` or `final_v4`.
- Model input observation does not prove that the draft repeats either confidential value.
- Exact-string replacement does not establish comprehensive removal of every conceivable sensitive derivative. No particular derivative is supported by the source, so inventing one would not justify another positive finding.
- The public fields contain neither confidential original string (`ticket.json:2–6`), so the stated replacement operation does not require changing those source public values.

Consequently, there is no independently supported residual user-output excess, and no additional output rewrite is warranted on the available evidence. This is not proof that every possible returned note is safe or semantically complete.

### F5 — No conversation-memory excess occurs in the specified workflow

T6 supplies no functional need for durable conversation memory. Although `context.save` is defined, it is never invoked. The private local objects do not constitute saved conversation memory (`CONTRACTS.md:13–16,48–49`; `SKILL.md:8–16`).

## 6. Concrete reduction and preservation argument

**Proposed change:** replace the ticket argument at `SKILL.md:10` with the already-computed masked version:

```text
draft_v3 = draft_model.compose(
    ticket=redacted_v2,
    style="one sentence; preserve any quoted error_text verbatim"
)
```

This is a proposal, not a description of the current call.

Its preservation argument is grounded in the supplied interfaces:

1. **Keep the required model action.** The same drafting model is called once, retaining T1.
2. **Keep all substantive issue inputs.** `redacted_v2` has the same fields and unchanged `product`, `error_text`, and `requested_fix` values (`CONTRACTS.md:27–34`), retaining T2.
3. **Keep the exact-error requirement.** Both the public error value and the style argument remain unchanged. The model’s exact-quotation contract continues to apply (`CONTRACTS.md:39–40`), retaining T3.
4. **Meet the required masking order.** The provider now receives `[EMAIL]` and `[SESSION_KEY]` at the two original field positions, with no original characters or reversible encodings in those replacements (`CONTRACTS.md:30–34`), satisfying T4.
5. **Keep the output path.** The existing local cleaner and single reply can remain. The original remains available only inside the controller for the documented cleaner (`SKILL.md:9,12–13`), retaining T5.
6. **Add no persistence.** The change introduces no save or additional call, retaining T6.

After this change, the request transmission, model observation, and retained provider request still exist, but their ticket payload is `redacted_v2`: the three unchanged public values and the two specified placeholders. This removes both supported confidential disclosures without relying on an unstated field-selection interface, isolation mechanism, or provider retention option.

The source does not promise byte-identical drafts when an argument changes. The preservation claim is that the required public inputs, documented drafting behavior, quotation constraint, call count, and final display path are preserved. No stronger claim of natural-language equivalence or global minimality is established.
