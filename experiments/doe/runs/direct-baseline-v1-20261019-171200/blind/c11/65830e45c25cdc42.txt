The workflow has one supported minimization defect: it sends `original_v1` to the drafting provider even though it has already created the required masked version. Consequently, both confidential values reach the external provider, its retained request, and the drafting model. The later assignment and draft cleanup cannot repair those earlier exposures. Passing `redacted_v2` to the same model call is a concrete correction that preserves the requested functionality.

This is a static conclusion about the documented workflow, not an observed execution. The central exposures are source-explicit; they do not depend on assuming implicit model access, tool logging, or additional network activity.

**Supported unnecessary exposures and correction.** The original email and original session key constitute two excess sensitive payload elements on the necessary drafting call. Both have the same supported path:

`ticket.json` → private `original_v1` → external drafting request → model observation and provider request retention.

Their existing inclusion is not evidence of necessity. The public fields provide the issue content, and the user specifically requires placeholders for the confidential fields. This finding rests on the concrete payload and available substitute, as well as the user restriction; crossing a boundary or violating a prohibition alone would not establish excess.

Replace step 3 with:

```text
draft_v3 = draft_model.compose(
    ticket=redacted_v2,
    style="one sentence; preserve any quoted error_text verbatim"
)
```

This is a proposed correction, not the current behavior. It uses an object and interface already defined by the source, with no assumed field-only getter, model-isolation mechanism, or provider option. `mask_fields` preserves all public issue fields exactly and supplies both required placeholders. The same documented model behavior and style preserve the one-sentence output and verbatim quoted error text. For this fixture, neither confidential literal occurs in the public fields, so the existing exact-match cleanup does not alter those public details. (`CONTRACTS.md:27–40, 42–44`; `ticket.json:2–6`.)

With that change, the provider receives and retains the masked ticket, and the model observes that masked version. It no longer receives either original confidential value through the documented request. The existing local cleanup and single reply can remain; no durable conversation memory needs to be added. Moving the later `working_ticket` assignment alone would only help if the model call were also changed to use the masked object.
