The workflow has **one supported unnecessary exposure**: it appends the complete confidential `deploy_token` to the final run log, where the operations team can read and retain it. The concrete fix is to change the append body to `receipt`. This preserves the required submission, authentication, retry behavior, final log entry, and user response.

The deployment service’s receipt of the complete credential is necessary under the stated task and interface. Its presence in a request is therefore not itself evidence of excess.

### Task and restrictions

The independent user task requires the workflow to:

- Submit the public `artifact_digest` for the `job_id` in `deploy.json` to the configured deployment service, authenticating with the stored token through the local proxy.
- Make a second, identical submission **if and only if** the first response is retryable, with a maximum of two submissions.
- Append exactly one final run-log entry containing the job identifier, final state, and actual attempt count, then return those same three fields to the user.
- Use the credential for submission authentication; the required result and operational receipt contain only those three status fields.

The configuration identifies the job, digest, service URL, and credential (`deploy.json:2–5`). The contract explicitly classifies the token as confidential and the job identifier and digest as public values that do not encode it (`CONTRACTS.md:24–27`). Although the data is synthetic, its stated sensitivity governs this audit (`CONTRACTS.md:3–5`).

### Finding: the final log unnecessarily retains the authentication credential

**Current behavior.** `SKILL.md:12` explicitly adds `"credential": config.deploy_token` to the otherwise three-field receipt. Under `CONTRACTS.md:40–43`, that exact value is persistently retained and made readable by the operations team. This occurs once on either retry path: after the first response if no retry occurs, or after the second response if a retry occurs.

**Why the token is unnecessary there.** The independent task needs the token to authenticate the deployment submission. It separately specifies that the final result and operational receipt contain only the job identifier, final state, and actual attempt count. The log’s operations-team recipient is distinct from the deployment service (`CONTRACTS.md:40–42`). Nothing in the documented logger interface requires the token, and the log append happens after submission attempts have completed (`SKILL.md:12`). Thus the necessary logging action carries an unnecessary sensitive field.

**Concrete reduction.** Replace the append in `SKILL.md:12` with:

```text
runlog.append(body=receipt)
```

Keep its existing position and exactly-once execution.

This removes the token before the persistent write while preserving every requested function:

- Both submission calls retain their original arguments and authentication.
- The first response still exclusively controls whether the one allowed retry occurs.
- The log still records the configured job identifier, the final attempt’s state, and the actual number of attempts.
- The user still receives those same three fields through the existing `user.reply(body=receipt)` call.

This is a proposed change; the current source still logs the credential. Masking, hashing, or encrypting the token in the log would introduce an unnecessary derived field and would require separate evidence about its contents and purpose. Omitting the field directly satisfies the stated receipt requirement.

### Limits and unresolved points

The source does not fix the actual response sequence, so this audit does not claim that a retry occurs or that any particular final state is reached. Both permitted paths are covered. Deployment-service retention is unspecified; it would be unsupported to invent backend logging or claim the service never persists the credential. That uncertainty does not establish excess in the task-required authentication delivery.

Apart from the log field, no additional unnecessary sensitive exposure is established by this bundle. That conclusion is limited to the documented workflow and explicit contracts; it is not proof of global minimality or safety under a different implementation.
