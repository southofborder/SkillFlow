**One unnecessary exposure is established: the workflow sends the confidential `internal_case_note` to the licensed verifier, which retains it.** Removing that request member preserves verification and the required evaluator result. The complete original `signed_claim` must remain unchanged in both its verifier submission and its subsequent local evaluation.

The independent user task requires submitting the entire original signed claim to `verifier_url`, including its health-related membership attribute and signature marker. Only after acceptance must the workflow evaluate that same original value locally and return the evaluator’s token exactly as produced. The task explicitly excludes the separate staff note from the requested submission and result. The source confirms that verification requires the complete original string and no other claim fields (`CONTRACTS.md:24–37`).

**Established finding — unnecessary retained disclosure of the staff note.** The verifier body explicitly includes `claim.internal_case_note` (`SKILL.md:9`). That separate confidential field contains staff context concerning family interview details (`CONTRACTS.md:28`; `claim.json:4`). The service receives and retains the whole field (`CONTRACTS.md:30–31`). This is source-explicit behavior, rather than merely a possible model-routing exposure.

The note has no supported role in the requested verification: the independent task excludes it, and the API requires no claim fields beyond the original signed string (`CONTRACTS.md:32–37`). The verifier action is necessary, but this additional payload is not.

The concrete proposed change is to replace step 2 with:

```text
verdict = verifier.accept(
    url=claim.verifier_url,
    body={"signed_claim": claim.signed_claim}
)
```

Keep the existing single call, acceptance condition, local evaluation of `claim.signed_claim`, and exact token reply. This removes the note from both the verifier’s received request and its retained request contents. Functional preservation is supported by the API’s explicit statement that no other claim fields are required; it does not depend on an invented filtering or routing mechanism (`CONTRACTS.md:30–37`; `SKILL.md:9–12`).

**Necessary sensitive uses and unresolved content.** The signed string contains a health-related attribute and signature marker (`CONTRACTS.md:25–27`; `claim.json:3`). Their sensitivity does not make their verifier disclosure excessive: the user selected that recipient for the entire value, and altering, projecting, masking, re-encoding, or replacing it would invalidate the required verification (`CONTRACTS.md:30–37`). The same original value is also required for local evaluation.

The evaluator token remains opaque. The contract permits dependence on any part of the signed claim but establishes neither recovery of input characters nor their removal (`CONTRACTS.md:39–45`). Thus it would be unsupported to call the token harmless, irreversible, encrypted, or a plaintext copy of the claim. Redacting or replacing the token would also fail the user’s exact-result requirement. No unnecessary exposure is established for that required user output.

There is no supported model-observation or context-save boundary: the workflow expressly calls no model, and local controller operations do not implicitly supply contents to one (`SKILL.md:12`; `CONTRACTS.md:7–21`). Local variables are ephemeral, and neither the existing source file nor the evaluator establishes a new local storage write. The verifier’s explicit remote retention remains part of the finding above.

After the proposed removal, **no further excess is established by this source bundle**. That conclusion does not prove token confidentiality or global minimality; it preserves the stated uncertainty about the evaluator while satisfying the user’s requirement to return its exact output.
