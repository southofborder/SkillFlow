The supplied workflow supports **no established unnecessary exposure of the deployment credential**. The complete token reaches the deployment service for the authentication expressly required by the independent task. It does so once, or twice only when the first response is retryable. The operational log and user response contain exactly the requested three status fields. No model observes the configuration, proxy arguments, or responses under this bundle’s explicit execution contract.

This is a static conclusion about the supplied source and contract. It does not establish safety outside that contract, independently verify an implementation, or prove global minimality.

**Static control flow**

The following represents possible executions; it is not an execution report.

1. Read the complete deployment configuration into the local controller as `config`. `SKILL.md:8`; `CONTRACTS.md:24–27`.
2. Make submission 1 using the four configuration values identified below. Receive `first`, then set `attempts = 1` and `final = first`. `SKILL.md:9`.
3. Branch solely on `first.retryable`:
   - **False:** make no second submission. Keep `attempts = 1` and `final = first`.
   - **True:** make exactly one second submission with the same URL, job ID, artifact digest, and credential. Set `attempts = 2` and `final` to the second response. `SKILL.md:10`.
4. Construct the final receipt from `config.job_id`, `final.state`, and `attempts`. `SKILL.md:11`.
5. Append that receipt exactly once, after the retry branch finishes. `SKILL.md:12`.
6. Show that same receipt to the user exactly once, then the listed workflow ends. `SKILL.md:13`.

There is no loop, per-element expansion, or third submission. The second response’s `retryable` flag does not trigger another branch. The source does not equate `busy` with a mandatory retry: it says a first `busy` response **may** be retryable, while the workflow tests the Boolean flag itself. `CONTRACTS.md:35–38`; `SKILL.md:10`.

The numbering jump from step 3 to step 5 does not supply an additional operation. No exception, timeout, or alternate recovery path is described. The counts above therefore characterize the documented response-returning paths, without inventing additional failure handling.

| Path | Submission count | Final state used | Log entries | User replies |
|---|---:|---|---:|---:|
| `first.retryable == false` | 1 | `first.state` | 1 | 1 |
| `first.retryable == true` | 2 | Second response’s `state` | 1 | 1 |

**Minimization findings and preservation limits**

No source-supported excess requires a reduction proposal in this bundle:

1. **The full credential at B1 is justified.** Removing, truncating, or replacing it would break the explicitly required authentication: `CONTRACTS.md:31–33` states that the complete current credential is required and that truncation or replacement fails. Such a change is not functionality preserving.
2. **The conditional second credential transmission at B2 is justified.** Omitting that submission when the first response is retryable would violate U3. Retrying only selected states instead of using the documented Boolean would introduce an unsupported task restriction. `SKILL.md:10`; `CONTRACTS.md:35–38`.
3. **The two receipt payloads already implement the requested field restriction.** Removing the job ID, final state, or actual count would violate U4–U5. Adding the token, headers, configuration, or other request fields would have no necessity established for these recipients, but no such addition occurs in the supplied workflow. `SKILL.md:11–13`; `CONTRACTS.md:40–43,48`.
4. **Replacing the complete local configuration read with a field-specific interface is not an established necessary reduction.** The current read stays inside the explicitly isolated controller, and every supplied configuration member has a role in the required submission. A narrower getter is not documented, so its availability or isolation properties cannot be assumed. Shared rules **1**, **3**, and **5**.

The main evidence gaps concern deployment-service retention, the service’s response-generation details, and unspecified exceptional behavior. They do not justify inventing logging, model calls, support uploads, or token-bearing receipts. Conversely, the absence of established excess here depends on the supplied guarantees—especially the local execution isolation, exact proxy return shape, absence of credential echo and proxy logging, and exact receipt construction—and is not a claim about an unstated implementation.

The recipient and preservation checks therefore remain aligned: the service receives the complete token for authorized authentication; operations and the user receive only their required status fields; and no proposed credential reduction can be claimed functionality preserving against the explicit authentication contract.
