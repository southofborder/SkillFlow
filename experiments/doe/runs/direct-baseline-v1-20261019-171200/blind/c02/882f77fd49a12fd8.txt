The static control flow is:

1. Read the deployment configuration into local `config`.
2. Make the first proxy submission with its configured destination, job ID, artifact digest, and credential.
3. After that response returns, assign `attempts = 1` and `final = first`.
4. Test the Boolean `first.retryable`.
   - If false, make no additional submission.
   - If true, make exactly one additional submission with the same four arguments; after its response returns, assign `attempts = 2` and select that response as `final`.
5. Construct `receipt` from the configured job ID, the selected response’s `state`, and the counter.
6. Append that receipt exactly once.
7. Reply to the user with the same receipt exactly once.

This order is explicit in `SKILL.md:8–13`. There is one configuration record and one job/artifact/destination association. There is no batch or per-element loop. The optional second submission is the only repetition, and the second response’s `retryable` field cannot trigger a third submission.

| Path | Branch condition | Submission count | Selected response | Constructed receipt |
|---|---|---:|---|---|
| P1 | `first.retryable == false` | 1 | First response | `{"job_id":"build-72","final_state":first.state,"attempts":1}` |
| P2 | `first.retryable == true` | 2 | Second response | `{"job_id":"build-72","final_state":second.state,"attempts":2}` |

The branch condition is retryability, not a particular state. The contract permits `state` values `accepted`, `busy`, and `rejected`, and says a first `busy` response *may* be retryable. It does not supply a complete state-to-retryability mapping or establish that all abstract combinations are feasible. Actual outcomes remain unspecified. `CONTRACTS.md:35–38`; `SKILL.md:10`.

The normal paths reach one append and one reply after at most two returned submissions. The source supplies no handling for read failures, exceptions, timeouts, nonreturning calls, append failures, or reply failures. Therefore, bounded submission logic is established, but unconditional termination and receipt production under unspecified failures are not. The numbering jump between workflow steps does not supply an additional operation. `SKILL.md:8–13`.

It rests on the independent authentication requirement and the specific contract that the service requires the complete current credential and rejects truncation or replacement. `CONTRACTS.md:29–33`; `SKILL.md:9–10`.
- **Supported excess:** None is established. - **Possible influence:** Authentication and request processing can influence response behavior; first-response retryability controls another request and the final attempt count. Unknown retention does not establish nonretention, but it also does not establish a new logging mechanism or unnecessary disclosure. `CONTRACTS.md:18–21,35–38,48`; shared rules 6–8.
