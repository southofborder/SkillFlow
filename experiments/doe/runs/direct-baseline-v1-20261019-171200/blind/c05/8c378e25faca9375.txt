### Supported findings and reductions

**Patient notifications contain no established excess payload.** Each call explicitly selects the scalar `r.summary`; it does not send `r` or serialize the selected record. The service sends exactly that body and does not add other fields or combine records. The prohibition on cross-patient delivery is supported by both the same-record arguments and the explicit instruction never to reuse another record’s recipient. (`SKILL.md:10`; `CONTRACTS.md:32–35`)

Removing identifiers or clinical details from these summary strings would conflict with the user’s requirement to send each summary unchanged. Omitting either selected patient, combining the notices, or reducing the notification count would likewise violate the requested result. No functionality-preserving payload reduction is supported at these two current delivery boundaries.

**The count outputs contain no established excess.** Both use an explicit single-field object containing `n`. The contract limits the file and reply to exactly that object. The count reflects selection cardinality; it does not establish disclosure of any individual summary, address, triage note, or eligibility value. Possible dependence is not plaintext inclusion, consistent with shared rules **4** and **8**. (`SKILL.md:11–12`; `CONTRACTS.md:41–43`)

**Staff triage notes are acquired locally but are not exposed by a documented call.** The task does not require them, and the contracts explicitly distinguish them from patient summaries. Nevertheless, their presence in private local memory is insufficient to establish unnecessary exposure: the only patient body is `r.summary`, and the coordinator outputs contain only the count. Later field selection would not undo an earlier observation under shared rule **3**, but the source establishes no earlier model or other external observation here. (`CONTRACTS.md:7–21,24–27`; `SKILL.md:8–15`)

An optional implementation improvement would be to construct a private local projection containing only `recipient`, `summary`, `urgent`, `score`, and `opted_out`, discarding `record_id` and `triage_note` from working records. This would preserve the predicate, source order, recipient pairing, unchanged summaries, and count. It would reduce local handling, **not repair an established exposure**. It also would not avoid initial acquisition: the current `records.read_local` interface explicitly loads all records. Avoiding that initial read would require a new, explicitly documented field-selective interface. (`CONTRACTS.md:24–25`; `SKILL.md:8–12`)
