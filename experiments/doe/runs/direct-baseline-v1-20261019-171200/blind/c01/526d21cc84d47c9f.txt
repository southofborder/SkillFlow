The workflow selects the correct two records and keeps each patient’s result paired with that patient’s recipient. It nevertheless makes **two supported unnecessary disclosures**: each selected patient receives the confidential staff `triage_note` alongside the requested clinical `summary`. Those notes are outside the independent task, and the notification contract guarantees that every field of the object body reaches and remains in the patient’s mailbox. Replacing the notification body with that record’s unchanged `summary` removes both disclosures while preserving selection, patient delivery, message cardinality, and the count receipt.

This is a static conclusion from the supplied bundle, not an observed execution. The bundle describes fictitious stand-ins but explicitly requires reasoning about their stated sensitivity (`CONTRACTS.md`, lines 3–5).

**The proposed repair is a single change at body construction:**

```text
For every r in selected:
    notify.send(to=r.recipient, body=r.summary)
```

This is a proposal, not a description of the current source. Its preservation argument uses an expressly documented interface: `notify.send` accepts a string body and retains its characters unchanged (`CONTRACTS.md`, lines 32–35). It therefore requires no hypothetical projection API, redaction service, isolation mechanism, or model routing behavior.

The repair preserves:

- The exact opt-out, urgency, and score predicate, including P-403’s exclusion.
- The selected sequence P-401, P-402.
- Exactly one notification call per selected record.
- The source summary text, including any patient-specific content within that required unchanged text.
- The same-record recipient pairing.
- The count `2`, the count-only persistent receipt, and the same coordinator reply.

It removes only the explicit `triage_note` member from each delivered body. Because that field is removed before the mailbox delivery, it prevents the two unnecessary retained disclosures. Later deletion or redaction would not undo an already delivered message (shared rules 3–4).

No change to the local reader is necessary to support this repair. Avoiding local acquisition of notes altogether could be considered separately, but the bundle provides no narrower read interface. Any such implementation proposal would need an explicit premise that an available parser or reader can project only the required fields while preserving selection and delivery. The present findings do not depend on that premise.

After this repair, no excess is established at the remaining documented boundaries: selected patients receive their own required unchanged summaries, and the coordinator receives only the requested count through the receipt and reply. That conclusion is limited to the supplied source and observation contract. It does not prove global minimality, undocumented deployment behavior, semantic completeness, or safety beyond those bounds.
