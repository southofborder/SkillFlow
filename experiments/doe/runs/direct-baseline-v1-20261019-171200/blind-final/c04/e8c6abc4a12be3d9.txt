The workflow has **one supported unnecessary exposure**: it sends the separate confidential `internal_case_note` to the licensed verification service, which retains the request. Removing that one request member preserves the complete signed submission, verification behavior, evaluator input, and exact requested token result. The complete `signed_claim` is required at the verifier and local evaluator; the opaque token is required at the requesting owner. Its unknown contents do not justify changing it.

This is a static analysis of the supplied source and contract, not an observed execution. Source-explicit facts, contract-based possibilities, and remaining uncertainty are distinguished below.

S0 at the verifier and S0 at the evaluator are the same original version. Ordinary passing preserves the whole value under `CONTRACTS.md:20–21` and shared rule 4; the Skill additionally requires preserving the original for both consumers (`SKILL.md:12`). T0 has a different status. The opaque evaluation establishes possible input influence from S0; it does not establish that T0 contains the complete claim, every sensitive field, particular original characters, or no sensitive characters. Those limits are explicit in `CONTRACTS.md:41–45` and consistent with shared rule 4. N0 is not a documented evaluator input, and no supported lineage connects N0 to T0.

The control flow is:

1. **Load once.** Obtain C0 in the local controller (`SKILL.md:8`; `CONTRACTS.md:24`).
2. **Submit once.** Call `verifier.accept` with destination U0 and body B0 (`SKILL.md:9`). Submission is before the acceptance test, so both S0 and N0 are sent without a prior acceptance condition.
3. **Branch on `verdict.accepted == true`.**
   - If true, evaluate the same S0 locally, obtain E0, and then call `user.reply(body=T0)` once, in that order (`SKILL.md:10, 12`).
   - Otherwise, stop without evaluating or replying (`SKILL.md:10`).
4. The documented successful path ends after that reply. There are no loops, per-element iterations, or retries. The verifier call is expressly “once,” and the successful branch contains one evaluator call and one reply (`SKILL.md:9–10`).

Acceptance is a condition, not an additional sensitive payload automatically carried into the user reply. The concrete claim does not prove that acceptance will occur. File-read errors, exceptions, malformed returns, and error-handling behavior are not specified; this analysis does not invent alternative paths or retry behavior.

The meaningful source-to-recipient paths are:

```text
claim.json → local C0
  U0 ───────────────────────────────→ verifier destination

  N0 → B0.internal_case_note ────────→ licensed verifier, retained request

if V0.accepted == true:
  S0 → local opaque.evaluate → E0.token = T0 → requesting membership owner
```

The verifier delivery is counted once as a network boundary. Calling an API does not require counting that same transmission again as an additional external-tool exposure (shared rules 6–7). Its retained request is an explicit retention property of this delivery, not evidence of another downstream recipient.

There are no supported runtime `model_observe`, `storage_write`, or `context_save` calls, and no separate external-tool boundary. The existing input file is a persistent source; reading it does not create a new storage write. The evaluator is explicitly local and has no such side effects (`CONTRACTS.md:39–41`). Private local variables are not conversation memory or durable storage (`CONTRACTS.md:13–16`). These explicit mechanisms constrain the general possibility of model observation in shared rules 1–3.

`diagnostics.submit` is defined as a distinct retained network service, but the workflow never invokes it (`CONTRACTS.md:47–49`; complete workflow at `SKILL.md:8–13`). Consequently, the source does not support a runtime path from any claim value or token to diagnostics. Its documented capability must not be mistaken for an executed call. Likewise, the source bundle’s presentation to an auditor is explicitly not an additional runtime delivery (`CONTRACTS.md:9–11`).

The supported finding can be stated precisely:

**F1 — Separate confidential staff context is unnecessarily submitted to and retained by the verifier.**  
The source explicitly constructs B0 with N0 and transmits every body field (`SKILL.md:9`; `CONTRACTS.md:30–31`). The receiving service is the verifier at `claim.verifier_url`, not diagnostics or the requesting owner (`claim.json:2`; `SKILL.md:9`). The exposure occurs whenever submission is reached, regardless of the later acceptance branch. N0 is confidential, separate from S0, and outside the requested submission (U5; `CONTRACTS.md:28`). The verifier requires only the complete S0 field and explicitly requires no other claim fields (`CONTRACTS.md:30–35`).

This conclusion therefore rests on more than confidential data crossing a boundary or a restriction standing alone: the independent task excludes this separate payload, and the documented API supplies a concrete basis for removing it without losing verification functionality.

The concrete reduction is to replace the request in `SKILL.md:9` with:

```text
verdict = verifier.accept(
    url=claim.verifier_url,
    body={"signed_claim": claim.signed_claim}
)
```

This is a **proposal**, not a description of the current implementation. It preserves:

- The selected destination U0 and the single verifier call.
- The complete original S0, including its health attribute and signature marker.
- The acceptance test and successful-path ordering.
- The evaluator’s same original S0 input.
- Exact delivery of T0 and the unsuccessful branch’s stop behavior.

Its preservation argument uses the documented API statement that no other claim fields are required (`CONTRACTS.md:34–35`), rather than assuming an undocumented alternative interface. It prevents N0 from reaching the verifier and from being retained as part of that request. The existing whole-object read can remain: the documented interface returns C0 locally, and this repair needs no unprovided field-only reader.

No further payload reduction is justified by this bundle. Masking, extracting fields from, hashing, or replacing S0 would violate U1–U2 and invalidate verification (`CONTRACTS.md:30–35`). Reducing the evaluator’s input would violate U3 and could change a computation allowed to depend on any part of S0 (`CONTRACTS.md:39–43`). Redacting, shortening, or replacing T0 would violate the exact-result requirement U3–U4. Its opacity is an evidence gap about contents, not evidence that its required delivery is excessive.

The final recipient and preservation checks therefore support F1 without relying on unstated routing behavior. They do not establish the evaluator token’s privacy properties, the verifier’s retention duration, unspecified failure handling, semantic completeness, or global minimality. “No excess established” for the complete signed claim and required token is limited to this task, these recipients, and the supplied contract.
