**One unnecessary sensitive-data exposure is supported:** if `first.retryable == true`, the workflow sends the complete deployment credential to a separate support vendor. Removing that support call preserves the requested authenticated submission, the bounded retry, and the final operational receipt. The credential’s use by the deployment service is necessary under the documented authentication contract.

This is a static conclusion about a conditional path, not evidence that the path has executed.

The independent user task requires:

- Submit the public `artifact_digest` for the configured `job_id` to the configured deployment service, authenticating through the local proxy with the stored credential.
- Retry the same submission exactly once if and only if the first response is retryable, with at most two submissions.
- Append exactly one final run-log entry and return exactly the same three status fields: job ID, final state, and actual attempt count.
- Use the credential to authenticate the job submission. The requested result and operational receipt contain only the three status fields.

The source identifies `deploy_token` as confidential and `job_id` and `artifact_digest` as public identifiers that do not encode the token. The shown configuration supplies all four proxy arguments; no additional runtime inputs need to be assumed. (`CONTRACTS.md:24–27`; `deploy.json:2–5`.)

**Finding and concrete reduction**

Delete the `support.submit(...)` operation at `SKILL.md:11`.

The exposure is source-explicit: this operation passes the original, complete `config.deploy_token`, and the support contract sends exactly that body to a separate vendor with retained, employee-readable requests. It is conditional on `first.retryable == true`; a nonretryable first response does not take this path. The source does not establish which response will occur, so this is a supported possible execution rather than an observed leak. (`SKILL.md:10–11`; `CONTRACTS.md:45–47`.)

The necessity judgment follows from the independent task and the documented function of the support service. The user requests deployment submission, its conditional retry, and a three-field receipt. The support service performs none of those submission or authentication functions. Removing its call therefore removes the unnecessary credential delivery while preserving:

- The first submission and its full authentication credential.
- The same four arguments on the second submission.
- The retry condition and maximum of two submissions.
- `attempts = 1` without a retry and `attempts = 2` with a retry.
- Selection of the final response, followed by one log append and one identical user reply.

This preservation argument relies on the package’s stated behavior: the support operation has no documented role in deployment submission or authentication, and its result is not used by the workflow. No undocumented support-side dependency is assumed. (`SKILL.md:9–14`; `CONTRACTS.md:45–47`.)

Removing only the `credential` member would eliminate the identified sensitive payload, but would retain an action outside the requested workflow. Removing the entire support call is the directly supported reduction. The proxy’s credential argument should remain complete because the source explicitly says replacing or truncating it causes authentication failure. (`CONTRACTS.md:29–33`.)

**Observation, influence, and evidence limits**

No model observation or context-save boundary is supported. The workflow explicitly calls no model, and the controller contract rules out implicit model observation, unmentioned logging, and telemetry. Those explicit routing limits displace the broader default possibilities in shared rules 2–3. Configuration and proxy requests otherwise remain ephemeral. (`SKILL.md:16–17`; `CONTRACTS.md:7–21, 34–35`.)

Authentication can affect response outcomes, and the first response controls whether a retry occurs. That possible influence does not show that the receipt contains credential plaintext: the response contract restricts its public fields and expressly excludes credential echoes. The receipt selects only the job ID, final state, and attempt count. Those fields are also expressly required by the task. (`CONTRACTS.md:35–38`; `SKILL.md:9–14`; shared rules 4 and 8.)

Actual response outcomes and deployment-service retention remain unspecified. No additional sensitive source, hidden credential copy, model call, or backend log is supported. Apart from the conditional support request, no excess sensitive exposure is established at the documented boundaries. That limited conclusion is not a proof of global minimality, semantic completeness, or safety outside this source bundle.
