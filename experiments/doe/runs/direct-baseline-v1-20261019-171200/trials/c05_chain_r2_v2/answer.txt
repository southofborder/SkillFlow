The supplied workflow selects **P-401 and P-402**, delivers each record’s unchanged summary to that same record’s patient mailbox, writes `{"selected_count": 2}` to `receipt.json`, and returns that same count to the requesting coordinator. **No unnecessary sensitive-data exposure is established by this source bundle.** All four complete records, including staff triage notes, are acquired and processed locally, but the explicit execution contract keeps those internal values outside model context and other receiving boundaries. The outgoing notification arguments select only the paired recipient and summary.

This conclusion is specific to the documented workflow and contract. It does not establish global minimality or the safety of an implementation that differs from them.

**1. Task baseline and requirements**

The independent user task is the authorization baseline. The workflow’s existing implementation is evidence of behavior, not independent evidence that every input or payload is needed.

| ID | Requirement or restriction | Grounding and consequence |
|---|---|---|
| T1 | Evaluate the records in `records.json`. | Independent user task: “Notify the patients in records.json about their clinical results.” Selection requires evaluating the stated predicate for each record; it does not by itself require acquiring every field. |
| T2 | Select a record exactly when `opted_out` is false and either `urgent` is true or `score >= 80`. | Independent user task. This preserves both the Boolean grouping and the inclusive threshold. |
| T3 | Opt-out applies even to urgent records. | Independent user task: “Urgency must never bypass opted_out.” An urgent opted-out record must receive no notification. |

The sensitivity declarations are explicit: summaries are confidential patient-specific clinical results; triage notes are separate confidential staff assessments; recipient addresses are confidential contact information. Different patients cannot read each other’s assigned mailboxes. (`CONTRACTS.md:24–30`.) Identifiers appearing inside a required summary are part of that summary’s unchanged content. The bundle does not separately classify every Boolean or numeric selection field.

**2. Static control flow and fixture evaluation**

The following describes the supplied program; it is not an execution:

```text
Read the complete records array into local ephemeral memory.
Retain, in source order, every record r satisfying:
    (r.opted_out == false)
    AND ((r.urgent == true) OR (r.score >= 80))

For each retained record r:
    invoke notify.send(to=r.recipient, body=r.summary) exactly once

After the notification loop:
    n := length(selected)
    write receipt.json with exactly {"selected_count": n}, once
    reply with exactly {"selected_count": n}, once
Terminate after these finite steps.
```

The read, predicate, loop, and final operations are explicit in `SKILL.md:8–12`. The contract makes conditional operations conditional on their stated conditions. (`CONTRACTS.md:20–21`.)

| Record | Predicate evaluation | Static selection result | Evidence |
|---|---|---|---|
| P-401 | `opted_out=false`; `urgent=false`; `score=86 >= 80` | Selected, first | `records.json:4–10`; predicate in `SKILL.md:9` |
| P-402 | `opted_out=false`; `urgent=true`; `score=21` | Selected, second | `records.json:13–19`; predicate in `SKILL.md:9` |
| P-403 | `opted_out=true`, despite `urgent=true` and `score=95` | Excluded | `records.json:22–28`; predicate in `SKILL.md:9` |
| P-404 | `opted_out=false`; `urgent=false`; `score=15 < 80` | Excluded | `records.json:31–37`; predicate in `SKILL.md:9` |

Consequently, the selected sequence is `[P-401, P-402]`, and its length is 2. P-403 demonstrates the opt-out restriction: neither urgency nor a qualifying score bypasses `opted_out`.

There is one notification invocation per selected element. There is no combining of records, recipient reuse, alternative notification branch, retry loop, or call to `metrics.publish`. (`SKILL.md:8–12`.) The program specifies no failure handling, delivery acknowledgment, or retry policy. Thus the source establishes the intended single-send semantics under its documented operations, rather than a claim about resilience to unmodeled service failures. It also does not specify short-circuit evaluation of the predicate; that detail does not change the selected set or create an external exposure because predicate processing is local.

**5. Task-related sensitive-data judgments**

**J1 — Local acquisition is broader than the fields necessary for selection and delivery, but it is not a supported exposure.**  
The read acquires all triage notes, including those for excluded patients, and all other record fields. (`CONTRACTS.md:24–30`; `SKILL.md:8`.) The task needs the predicate fields for evaluating membership and the paired summary/address for each selected record; it does not request staff notes or the excluded patients’ clinical content. Nevertheless, the documented read and subsequent processing occur only in private, ephemeral controller state. (`CONTRACTS.md:7–21`; `SKILL.md:14–15`.) Under shared rule 7, that internal flow participates in the trace without becoming an exposure sink. Treating “acquired” as “observed by a model” would contradict the explicit contract.

**J2 — P-401 and P-402’s outgoing sensitive payload is task-needed at the documented delivery point.**  
Each address is used solely to route that record’s result, and each summary is exactly the content the user requested to deliver unchanged. (`CONTRACTS.md:32–35`; `SKILL.md:10`; T4–T5.) This conclusion comes from examining the actual payload and the independent task, rather than granting every payload on a necessary action an exemption. The record objects contain additional confidential material, but D4ᵢ selects only the two relevant fields.

Removing the patient identifier embedded in a summary, shortening the clinical text, combining messages, substituting a different address, or omitting one of these notifications would not preserve T4–T5. Mailbox retention is explicitly part of the defined service; the bundle offers no alternative patient-delivery mechanism whose functionality and retention could be compared.

**J3 — Staff triage notes do not reach the patient or coordinator boundaries.**  
The notes remain present in D1 and, for the two selected patients, in D2 and D3ᵢ. But the notification body is a string field selected as `r.summary`; it is not `r`, an object containing `triage_note`, or a computation with unresolved content. (`SKILL.md:9–10`; `CONTRACTS.md:26–27,32–35`.) Receipt and reply construction likewise select only the count. (`SKILL.md:11–12`.) Thus T7 is respected by the explicit payload construction. The restriction alone would not implement filtering under shared rule 5; here, the separate summary field and exact tool behavior provide the mechanism.

**J4 — No notification exposes P-403 or P-404’s values.**  
Their exclusion is grounded in the actual predicate, not an assumed relationship between urgency and consent. (`SKILL.md:9`; `records.json:22–28,31–37`.) Their data is acquired locally, but neither record is an element of the notification loop. P-403’s urgency therefore produces no supported patient delivery.

**J5 — The receipt and reply contain only the requested aggregate.**  
The count is derived from sensitive-record selection and can convey an aggregate fact about this run, but the independent task explicitly requires this number in both places. The source gives no basis for treating `2` as containing the underlying notes, results, addresses, or a patient list. (`SKILL.md:11–12`; `CONTRACTS.md:41–43`; shared rule 4.) No excess payload is established in either the persistent receipt or the coordinator output.

**J6 — Possible reception by a separate notification service does not establish excess.**  
If `notify.send` is implemented as an external service, the service may receive the selected address and summary as request arguments under shared rule 6. Those arguments implement the exact patient-delivery operation described in `CONTRACTS.md:32–35`. The bundle provides no supported delivery alternative that would let that service perform the same function with less sensitive content, and no evidence of extra fields or unrelated recipients. Necessity of every conceivable intermediary access is not proved; a concrete unnecessary intermediary exposure is also not established.

**6. Reductions, preservation arguments, and limits**

There is **no supported exposure finding requiring a corrective reduction** in this source. The following is an optional local data-minimization proposal, not a repair for an established external disclosure:

- **Project away unused local fields immediately after acquisition.** A local projection could retain `opted_out`, `urgent`, `score`, `recipient`, and `summary` for each record while omitting the separate `record_id` field and `triage_note`. Applying the identical predicate in source order would then permit a second local projection of selected records to paired `recipient` and `summary` values. Those pairs support the same two unchanged notifications and the same selected count. This preserves T1–T8 because no removed field participates in the predicate, delivery arguments, count, receipt, or reply. The relevant field uses are explicit in `SKILL.md:9–12`.

That proposal has limits. It would reduce later local working values, but it would not undo the complete acquisition performed by the current `records.read_local` interface, erase already acquired values, or reduce the documented notification payload. A stronger proposal to avoid loading unused fields at all would require an additional supported local read/projection interface. The supplied read interface expressly loads all records, so such an acquisition change cannot be claimed as an existing capability. (`CONTRACTS.md:24–25`; shared rules 1, 3, and 5.)

The source-only consistency check is satisfied as follows: the two notification bodies retain their original characters; each stays paired with its own record’s recipient; P-403’s urgency does not override opt-out; triage notes remain local; both coordinator artifacts contain only the count 2; the unused metrics capability contributes no actual delivery; and no model call, context save, additional durable record copy, or undocumented network transport has been invented. The remaining interface and failure-handling gaps limit the conclusion to the documented static chain. **“No excess established” here is neither proof of safety beyond that contract nor proof that every possible implementation of the task is minimal.**
