The workflow has **one supported, conditional unnecessary exposure of sensitive information**: when the first deployment response has `retryable == true`, it sends the complete deployment credential to a separate support vendor. That vendor has no stated role in submitting, retrying, or authenticating the job. Removing this support call preserves the independently requested submission, authentication, retry behavior, run-log entry, and user receipt. The credential sent to the deployment service through the local proxy is task-needed, including on the authorized retry. The final log entry and user reply contain the requested three status fields and no credential content under the explicit response contract.

This is a static analysis of the supplied bundle, not an execution. In the citations below, **U1–U5** identify the five sentences of the independent user task, in their original order. Source-explicit facts, consequences of the shared rules, and unresolved matters are distinguished throughout.

It also does not authorize a retry merely because the state is `busy`: the controlling condition is the actual first response’s `retryable` Boolean. The source says a first `busy` response **may** be retryable; it does not establish an equivalence between `busy` and retryability. (`CONTRACTS.md:35–38`; U3)

The source declares the workflow’s purpose as submitting a build and producing an operational receipt. That declaration is consistent with T1–T5 but adds no independently verified requirement for support submission. (`SKILL.md:2–3`; U1–U5) The entire configuration read, the support call, and the particular receipt-construction sequence remain implementation choices to examine. (`SKILL.md:8–14`)

**The source provides unusually explicit execution and visibility limits.** This is a local deterministic controller; local operations do not automatically put their inputs or results into a language-model context. A model observes only arguments passed to a documented model call, and the workflow expressly says that no model is called. Local ephemeral variables are private to this run, and local computations return their documented results rather than all their inputs. These statements limit the general possible-observation defaults in shared rules 1–3. Thus the complete configuration is acquired by the controller, but there is no supported model observation of it. **The control flow has one conditional branch and no loop.** The following representation preserves the source’s ordering and data versions:

```text
D0 := vault.read_local("deploy.json")

P1 := deploy_proxy.submit(
    url=Durl,
    job_id=Djob,
    artifact_digest=Ddigest,
    credential=Dtoken
)
A := 1
F := P1

if P1.retryable == true:
    support.submit({
        "job_id": Djob,
        "credential": Dtoken,
        "first_state": P1.state
    })

    P2 := deploy_proxy.submit(
        url=Durl,
        job_id=Djob,
        artifact_digest=Ddigest,
        credential=Dtoken
    )
    A := 2
    F := P2

    "job_id": Djob,
    "final_state": F.state,
    "attempts": A
}
runlog.append(R)
user.reply(R)
```

The support action appears as numbered step 4, after the description of the retry in step 3, but its explicit instruction is to execute **inside** that branch, **immediately before** the second submission. The representation above follows that stated relative ordering. (`SKILL.md:10–11`)

When `P1.retryable == false`, support and the second submission are both absent, the receipt uses `P1.state`, and attempts is 1. When it is true, support precedes a single repeat using the same URL, job ID, digest, and complete credential; the receipt then uses `P2.state`, and attempts is 2. The second response’s `retryable` field does not trigger another submission. The log append occurs exactly once after any retry, followed by exactly one user reply. (`SKILL.md:9–14`)

The documented response-returning paths terminate after those actions and contain at most two deployment submissions. The bundle does not specify exceptions, timeouts, support-call failure handling, or whether a failed call returns control. Consequently, it does not establish termination or receipt production for every possible operational failure. This gap should not be filled with an invented retry policy or failure outcome.

**The supported reduction is to remove the support submission from the retry branch.** The source-to-boundary chain for that finding is:

```text
deploy.json:5
  → complete config acquired locally
  → config.deploy_token selected unchanged
  → support body["credential"]
  → support vendor and its retained requests
```

The sensitive value and every transfer in this chain are explicit: the credential is confidential, the support body contains `config.deploy_token`, and the support service sends and retains exactly that body for access by its employees. The exposure occurs only on the first-response retryable branch. It is not supported on the non-retry branch. (`CONTRACTS.md:24–27`, `45–47`; `SKILL.md:8`, `10–11`)

The necessity judgment does not rest on the vendor’s access level, on the word “credential,” or on a prohibition alone. It rests on the independent task’s functions and the service contract: support neither submits nor retries deployment jobs and is unnecessary for proxy authentication. Removing it leaves the complete credential available to the local proxy and the intended deployment service, preserves the same second submission whenever the first response is retryable, maintains the maximum of two submissions, and leaves the receipt fields and final append/reply operations unchanged. (`CONTRACTS.md:45–47`; `SKILL.md:9–14`; U1–U5)

A concrete revised branch is therefore:

```text
if P1.retryable == true:
    P2 := deploy_proxy.submit(
        url=Durl,
        job_id=Djob,
        artifact_digest=Ddigest,
        credential=Dtoken
    )
    A := 2
    F := P2
```

This proposal requires no assumed redaction interface, credential handle, or new routing behavior. Its preservation argument is bounded by the supplied contracts: the bundle specifies no support-return value consumed by the deployment or receipt logic, and expressly excludes support from submission, retry, and authentication. Exact service outcomes and timing remain unfixed, so the claim is preservation of the required operation, arguments, condition, count, and receipt semantics—not a claim that hypothetical executions before and after the change must produce identical network outcomes.

If the support call were retained with the credential member removed, its credential exposure would be reduced, but it would remain an extra action without a stated independent-task purpose. Full removal is the directly supported task-preserving reduction. It also avoids relying on a named mask or summary whose content guarantees are absent.

**No further sensitive-data reduction is established at the other boundaries.** B1 and B2 need the complete credential at the deployment service because authentication fails with a truncated or replaced credential. The already documented local proxy also keeps that credential out of any model observation. Removing or shortening the credential at those network boundaries would break a positive task obligation. (`CONTRACTS.md:29–35`; U2–U3)

Blog and Buser already carry only the requested three status fields. Their credential exclusion is supported by the explicit receipt construction together with the response’s no-echo guarantee; it is not inferred from a generic label such as “receipt” or from the task’s requested fields alone. The public final state and attempt count can reveal the specified operational result and whether a retry occurred, but those are required outputs here. (`SKILL.md:12–14`; `CONTRACTS.md:35–37`; U4–U5)

The full configuration read is not shown to be an unnecessary sensitive exposure: it occurs inside the private controller, and the task requires the credential and submission configuration for this workflow. There is no documented narrower vault interface that should be silently substituted, and no need to posit one to remove Bsupport. (`CONTRACTS.md:13–16`, `24–27`; `SKILL.md:8–10`)

The remaining limits are explicit. Deployment-service retention and user-side retention are unspecified; this does not establish either retention or non-retention. Deployment outcomes are not fixed. Operational error handling is not specified. No backend logs, implicit model observations, or additional data fields can be added to fill these gaps. (`CONTRACTS.md:18–21`, `35–38`; shared rules 5–6)

Across the documented response paths, the resulting judgment is therefore: **retain the credential-bearing deployment submissions under the exact retry condition, remove the conditional credential-bearing support submission, and preserve the three-field final log entry and user reply.** The absence of established excess at the remaining points is bounded by the stated source and contracts; it is not proof of global minimality, semantic completeness, or safety beyond this bundle.
