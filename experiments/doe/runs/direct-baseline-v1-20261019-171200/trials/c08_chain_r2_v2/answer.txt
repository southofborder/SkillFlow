1. **P2 requires the entire sensitive signed claim at the licensed verifier; no excess is established in this request.**

   `S0` contains the health-related membership attribute, owner identifier, expiry information, and signature marker as one confidential signed record. The independent task expressly selects the licensed service as recipient of the original complete value, including the health attribute and signature marker. U1–U2. The API requires byte-for-byte equality and rejects editing, masking, field projection, re-encoding, or hash substitution; it requires no other claim fields. `CONTRACTS.md:30–37`.

   The current body contains exactly that required field. `SKILL.md:9`. Sending only a supposedly sufficient entitlement attribute, removing the health information, replacing the signature marker, or submitting a hash would violate both the requested protocol and the API contract. No such reduction preserves the required function. The fact that the service retains the request and is another recipient does not by itself establish unnecessary exposure. There is no documented retention-control interface that would support a concrete retention change.

2. **P4 requires the same original claim as the evaluator’s local input; it does not create a separate external or model exposure.**

   The task explicitly requests evaluation of `S0` after acceptance. U3. The specification permits the computation to depend on any part of `S0`; it does not establish which input characters, if any, appear in `T0`. It also does not establish irreversibility, masking, or encryption. `CONTRACTS.md:39–45`. Therefore, neither “the token contains the whole claim” nor “the token removes the sensitive information” is justified. Shared rule 4.

Truncating, masking, hashing, or replacing `T0` would no longer return the requested token. There is no supported functionality-preserving reduction to propose for this output from the available evidence.
