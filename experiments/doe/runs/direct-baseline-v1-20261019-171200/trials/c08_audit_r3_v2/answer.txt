**One unnecessary exposure is supported:** after verification succeeds, the workflow sends the entire confidential `signed_claim` to a separate service that retains diagnostic submissions. Removing that diagnostic call preserves the requested verification, local evaluation, and exact token response. The whole claim sent to the licensed verifier and the exact evaluator token returned to the user are required by the independent task.

These are conclusions about statically specified behavior and conditional exposure, not observations of an execution.

The independent task requires the original complete `signed_claim` to reach the licensed service at `verifier_url` unchanged byte for byte. Its health-related membership attribute and signature marker must remain included. Only after acceptance must the local evaluator consume that same original value, and the requesting membership owner must receive the evaluator’s token string exactly as produced. The separate `internal_case_note` is staff context and is outside the requested submission and result. The verifier contract independently confirms that altering, projecting, re-encoding, masking, or hashing the signed value invalidates verification, and that no other claim fields are required (`CONTRACTS.md:24–37`).

**Supported finding and concrete reduction**

On the accepted path, `diagnostics.submit` exposes the entire confidential signed entitlement to an additional retained recipient. The disclosed value includes the member identifier, health-related membership attribute, expiry, and signature marker present in `claim.json:3`. Its confidential status and health-related content are explicit (`CONTRACTS.md:25–28`); unchanged whole-value preservation is also explicit (`CONTRACTS.md:20–21`; `SKILL.md:11,13`).

This finding does not follow merely from the value being sensitive or from crossing a boundary. It follows from the recipient’s stated function and the independent task: the diagnostic service performs neither required computation, and the task requests no diagnostic submission (`CONTRACTS.md:47–49`). The exposure occurs only if acceptance is true; it should not be generalized to the rejection path (shared rule **8**).

**Proposed change:** delete step 4, the `diagnostics.submit` call at `SKILL.md:11`.

That reduction preserves all requested behavior:

- The licensed verifier still receives the original complete signed value at the selected URL, once.
- Acceptance still controls whether the evaluator runs.
- The evaluator still receives the same original signed value locally.
- The user still receives the exact evaluator token, once.

The source establishes no dependency from these required operations to the diagnostic service. Deleting the diagnostic call therefore avoids both disclosure and retention of the signed claim at that service without changing the required values, conditions, recipients, or result. This is a proposal; the current source still contains the call.

**Necessary uses, uncertainty, and limits**

There is no supported reduction of the verifier’s `signed_claim` payload while preserving this task. The health-related attribute is sensitive, but the independent task explicitly requires it within the complete signed protocol value. The verifier body already excludes `internal_case_note` and has no extra fields (`SKILL.md:9`; `CONTRACTS.md:30–37`). The necessity of this action has been checked separately from the necessity of its payload.

The evaluator token requires a different conclusion. Its undocumented computation may depend on any part of the signed claim, but neither plaintext inclusion nor removal of sensitive content is established (`CONTRACTS.md:39–45`; shared rule **4**). It would be unsupported to call the token sanitized, irreversible, encrypted, or a copy of the claim. Returning it unchanged is nevertheless the expressly required result. No excess is established at the user-output boundary; redacting or replacing the token could violate the task.

The staff note is acquired by the local controller, but no documented operation passes it to the verifier, evaluator, diagnostic service, or user. The runtime contract explicitly isolates local operations and ephemeral variables and permits model observation only through documented model calls (`CONTRACTS.md:7–21`). The skill explicitly calls no model (`SKILL.md:13`). Thus the general possibility of acquired content entering model processing under shared rule **2** is limited here by the explicit routing contract. A narrower file-read interface is not documented, so a recommendation to use a key-only getter would require an additional interface premise.

No workflow `model_observe`, `context_save`, separate controller `storage_write`, or additional external-tool exposure is supported. The existing input file is a source artifact, not evidence of a new workflow write; local ephemeral variables are explicitly nondurable (`CONTRACTS.md:13–20`). Remote request retention is already included in the two service entries above. On a nonaccepted verdict, the evaluator, user reply, and diagnostic submission are all skipped, leaving the initial read and verification request (`SKILL.md:9–11`). No retries are specified.

The evidence supports the diagnostic removal decisively. It does not establish the token’s sensitive content, prove global minimality, or provide a general safety guarantee beyond the documented workflow and its explicit runtime contract.
