The toolkit’s public entry is `skill/scripts/src/index.ts`: it exports the high-level functions and re-exports the six API modules, client utilities, storage, and settings. The Skill shows imports from `./scripts/src/index.js` and direct execution with `npx tsx scripts/src/index.ts`. Direct execution only prints help when `process.argv[1]` exactly equals the module URL’s pathname; there is no CLI dispatch to an analysis function. The setup script changes to its own directory and runs `npm install`; the package is ESM and declares Node ≥18. The Skill calls for a project-root `.env`, three enabled Google APIs, and a service account with GA4 and Search Console access. (`skill/SKILL.md:8–51`; `skill/scripts/setup.sh:1–2`; `skill/scripts/package.json:1–17`; `src/index.ts:12–46,364–405`.) Below, `src/` means `skill/scripts/src/`.

**Configuration and shared state.** At module initialization, `dotenv.config()` loads from the current working directory. Later `getSettings()` calls read the resulting environment: `GA4_PROPERTY_ID`, `GA4_CLIENT_EMAIL`, `GA4_PRIVATE_KEY` (literal `\n` becomes a newline), `GA4_DEFAULT_DATE_RANGE` (fallback `30d`), and `SEARCH_CONSOLE_SITE_URL`; storage uses the current working directory’s `results` directory. Each of the three client getters returns its existing handle on a cache hit. On a miss, it validates property ID, email and key, then creates and caches a handle or throws on failed validation. The site URL is not validated there. GA4 receives the email and key through `BetaAnalyticsDataClient` from `@google-analytics/data`. Search Console `v1` and Indexing `v3` use their respective `@googleapis/searchconsole` and `@googleapis/indexing` factories; each cache miss constructs its own `google.auth.GoogleAuth` from `googleapis` with the email, key, and both `webmasters.readonly` and `indexing` scopes. Requests obtain `properties/<current property ID>` or the current site URL separately, so an existing handle retains its creation credentials even when request settings change. `resetClient()` clears all three handles. (`src/config/settings.ts:5–9,40–74`; `src/core/client.ts:6–133`.)

**URL loops.** Each loop tests for another member of the caller’s `urls`; on true it takes the current URL, awaits the child call, and returns to the test after a handled outcome. On false it exits to the batch save and return, including for an empty input. `requestIndexingBatch(urls, options?)` calls `requestIndexing(url, {save: false})`, collects notifications, and optionally saves `indexing/batch_indexing`; a child rejection escapes before the aggregate save. `reindexUrls(urls)` makes the same child call and adds `status: submitted` plus the returned notification, whose URL can replace the input URL. Its catch produces a `failed` record with the input URL and stringified exception. `checkIndexStatus(urls)` calls `inspectUrl(url, {save: false})`; success retains the input URL, sets `indexed` only for verdict `PASS`, and stores `indexStatus`. Its catch retains the input URL with `indexed: false` and an error in `status`. The two high-level loops continue after caught errors and save `indexing/reindex_batch` and `indexing/index_status_check`, respectively. Their aggregate saves are outside the per-URL catches. (`src/api/indexing.ts:89–105`; `src/index.ts:301–345`.)

**Saving, reading, and the unresolved link.** `saveResult(data, category, operation, extraInfo?)` creates the category directory as needed, writes `{metadata, data}` as JSON, and returns the path. Metadata records ISO `savedAt`, category, operation, the current property ID, and truthy extra information. The filename uses local time to the second, a sanitized operation, and optional sanitized extra information; a write to the same path replaces it. The analysis call sites discard the returned path. Independently, `listResults(category, limit?)` lists `.json` paths in descending filename order and slices if a limit is defined; a missing directory gives `[]`. `loadResult(filepath)` acquires and parses file contents as the saved wrapper, returning `null` for an absent file or a caught read or parse failure. `getLatestResult(category, operation?)` lists paths, optionally filters by a sanitized substring in the path, and loads the first match, or returns `null`. The Skill’s examples pair `listResults('reports', 10)` with `loadResult(files[0])` and separately show `getLatestResult('reports', 'site_overview')`. They do not establish which file belongs to a particular invocation. The Skill requires analyze → auto-save → read saved JSON → write a Markdown summary with tables, trends, and recommendations in `results/summaries/`. No supplied implementation links a run to a later read or writes that summary. (`src/core/storage.ts:28–171`; `skill/SKILL.md:53–64,116–142`.)

The source retains several documentation and implementation differences. The Skill describes automatic saving for all results, while the implementation has the explicit save and early-return conditions above and also writes a `metadata` category omitted from the Skill’s directory sketch. The reference lists report filters and ordering, though the request omits both. The reference describes Search Console top pages by impressions; the entry-point help and SEO log say clicks, while the request supplies neither sort criterion. The Skill broadly presents relative date formats, while Search Console documents a calendar-date requirement and its parser forwards object values unchanged. These differences do not establish additional request behavior or remove the Skill’s summary phase.
