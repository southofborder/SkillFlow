# Links, Images, and Anchors

Links fail in three ways: the destination is malformed (parens, spaces), the reference is missing (silent literal text), or the path resolves against a root you did not expect. Anchors fail in exactly one way: the slug was generated by a rule you did not use.

## Destinations That Break

| In the URL | Symptom | Fix |
|---|---|---|
| A space | Link ends at the space; the rest becomes text | `%20`, or wrap the destination in `<…>` |
| `(` or `)` | Destination ends at the first unbalanced paren — Wikipedia URLs are the classic | `%28` / `%29`, or `<…>` |
| A `<` or `>` | Parsed as HTML | Percent-encode |
| A `"` | Starts a title attribute | Percent-encode |
| A trailing `.` or `,` from prose | Included in the URL, 404 | Move the punctuation outside the brackets |
| A bare `_` or `*` in a bare URL | Emphasis inside an autolink | Use bracket syntax, or `<…>` |

Angle brackets are the general escape: `[text](<https://en.wikipedia.org/wiki/Markdown_(disambiguation)>)`. They also permit spaces, which percent-encoding is still preferable for — spaces in a URL are a sign the file name should be renamed.

Titles are the third element: `[text](url "Title")`. They become `title=` in HTML and show as a tooltip; nothing else uses them, and screen readers may or may not announce them (`accessibility.md`).

## Inline vs Reference Links

```markdown
[inline](https://example.com)
[collapsed][]         and its definition   [collapsed]: https://example.com
[full][ref]                                [ref]: https://example.com "Optional title"
[shortcut]                                 [shortcut]: https://example.com
```

- Reference labels are **case-insensitive** and whitespace-normalized: `[Ref]` matches `[ref]:`.
- A missing definition **fails silently** — the source renders as literal `[text][ref]`. Nothing warns, no build breaks. This is the single most common broken-link bug in long documents, and the reason `link_style: inline` is the default.
- Definitions may sit anywhere in the file, including inside the block that uses them; the convention is at the bottom, or at the end of the section that uses them so that moving the section moves the links.
- Reference style earns its place when the same URL appears many times, when URLs are long enough to wreck a hard-wrapped file, or when a table's cells would otherwise be unreadable.

## Autolinks

- `<https://example.com>` is CommonMark: an explicit autolink, always works, requires the scheme.
- Bare `https://example.com` is a **GFM extension** (autolink literals) — it also picks up `www.` prefixes and email addresses. Not in CommonMark, not in Python-Markdown without `magiclink`.
- GFM autolinking stops at certain trailing characters (`.`, `,`, `:`, `)` when unbalanced), which usually does the right thing in prose and occasionally truncates a URL that legitimately ends in a paren.
- In MDX, `<https://example.com>` collides with JSX parsing — use bracket syntax there (`mdx.md`).

## Anchors and Slug Rules

Every heading becomes an id, generated by the target's rule. The rules differ, so **an anchor copied from one target to another is a broken link**.

| Target | Rule | `## Set-up: "Fast" mode (v2)` becomes |
|---|---|---|
| GitHub | Lowercase, strip everything except alphanumerics, `-`, `_`, spaces; spaces → `-`; duplicates get `-1`, `-2` | `#set-up-fast-mode-v2` |
| Python-Markdown `toc` | Lowercase, strip punctuation, spaces → `-`; duplicates get `_1` | `#set-up-fast-mode-v2` |
| Pandoc | Lowercase, strip punctuation, spaces → `-`, **leading digits dropped** | `#set-up-fast-mode-v2` |
| Docusaurus/kramdown/Pandoc with explicit id | Whatever you pin with `{#id}` | `#stable-id` |
| Confluence, Notion | Their own, opaque and unstable across edits | Copy the link from the UI |

Practical rules:

- **Derive, never invent**: write the heading, apply the rule, and verify by clicking. Emoji, code spans, and links inside headings all mangle the slug — `## \`config.yaml\`` becomes `#configyaml` on GitHub.
- **Pin the id where the target supports it** (`## Title {#stable-id}`, Docusaurus/MkDocs/kramdown/Pandoc). This decouples the URL from the wording and is the only durable fix for public documentation.
- On GitHub, where `{#id}` does not work, an HTML anchor above the heading (`<a id="stable-id"></a>`) survives the sanitizer and gives the same guarantee, at the cost of raw HTML.
- Cross-file anchors: `../guide/setup.md#install` on GitHub, but a docs generator rewrites `.md` to a route, so the same link inside a built site may need `/guide/setup#install`. `docs-sites.md` per generator.

## Surviving a Heading Rename

A rename is a breaking change to every inbound link, including bookmarks and links from outside the repo that nobody can grep. The procedure:

1. Compute the old slug and the new one.
2. Grep the repo for `#<old-slug>` — cross-links, the TOC, code comments, tests that assert on docs.
3. Search issues/PRs and any sibling site for the old anchor if the page is public.
4. Leave a stub where inbound external links are plausible: `<a id="old-slug"></a>` immediately above the heading, or a redirect if the generator supports one.
5. If the page has an explicit id, rename the heading text freely and leave the id alone — that is the whole point of pinning it.

## Relative Paths and Where They Resolve

| Context | `./setup.md` resolves against |
|---|---|
| GitHub file view | The file's directory in the repo, at the current branch or tag |
| npm package page | npmjs.com — repo-relative links break unless absolute |
| PyPI project page | pypi.org — relative links break; PyPI does not resolve them |
| Docs generator | The site's route table, after `.md` → route rewriting |
| Raw file / `raw.githubusercontent.com` | The raw host, no rendering at all |
| Local preview | Your filesystem, which is why local previews miss all of the above |

Rules that follow: docs that live and render only in the repo use relative links (they survive forks and branches); anything that also renders off-repo uses absolute URLs **pinned to a tag or a commit**, not to `main` — a branch URL points at whatever that file becomes later (`readmes.md`).

## Images

- Syntax is a link with a bang: `![alt](path "title")`. Everything above about destinations applies to the path.
- **Alt text is not optional** — it is the text screen readers announce and what renders when the image 404s. Write what the image is *for*, not what it depicts; use `![](…)` deliberately empty only for pure decoration (`accessibility.md`).
- No size control in Markdown. `<img width="480" …>` is the usual workaround and is HTML, so it depends on `raw_html` and the target's sanitizer. Some parsers accept `![alt](img.png =480x)` — it is non-standard, and silently renders the `=480x` as part of the URL where unsupported.
- Animated GIFs and large PNGs are the main weight in a README; the page loads them before anything else. Prefer SVG for diagrams, and keep screenshots under a few hundred KB.
- On GitHub, images in **private** repos are served through an authenticated proxy — a raw URL that works for you 404s for a logged-out reader, and that difference is invisible until someone reports it.

## Dark Mode and Theme-Aware Images

A diagram with a white background is unreadable in dark mode, and Markdown has no conditional syntax. Options, in order of durability:

1. **Make the image theme-neutral**: transparent background, mid-tone strokes. Works in every target with no special syntax; almost always the right answer.
2. **`<picture>` with a `prefers-color-scheme` media query** — GitHub renders it; most other targets keep the fallback `<img>`. Requires `raw_html`.
3. **Mermaid instead of an image** where the target supports it: the diagram inherits the theme (`extensions.md`).

## Link Checking

Automate it; humans do not click 400 links. A checker runs over the built site or the raw files, follows redirects, and reports status codes.

- Check external links on a cadence (monthly is the usual default), not on every commit — external sites rate-limit checkers and a red CI that everyone ignores is worse than no CI.
- Check **internal** links and anchors on every commit: they are free to verify and they break constantly, especially anchors after a heading edit.
- Expect false positives from sites that block bots (403 to any non-browser agent) and from anchor checks on JavaScript-rendered pages. Maintain an ignore list with a reason per entry, not a blanket skip.

**Write every sweep**: a row in `~/Clawic/data/markdown/checks/<year>.md` with the date, scope, tool, what it found, what was fixed and what was deliberately left, and the date into the `## Due` table of `memory.md` (`memory-template.md`). A link check with no previous run is a number; with one it is a trend, and the trend is what tells you whether the docs are being maintained or just written. Recurring external breakage earns a `## Quirks` line naming the source, so the next sweep does not re-diagnose it.
