# 传播 v1 三例实测：助手逐例复核

本报告由助手检查最终接受响应、源文、CFG、联合标注和实际传播记录后编写，不是用户人工确认，也不是模型的第二次裁判结果。没有增加模型调用，没有修改原响应或据此重标。没有读取或引用模型的隐藏推理过程。

## 1. 工程结果与方法结果分开看

| 样例 | 标注执行状态 | 传播状态 | 已记录 IR | Data 数 | 模型未决项 |
| --- | --- | --- | ---: | ---: | ---: |
| 001 / N01 | complete | complete | 12 / 12 | 7 | 0 |
| 010 / Q04 | incomplete | complete | 18 / 18 | 18 | 4 |
| 013 / F01 | complete | complete | 18 / 18 | 20 | 0 |

三例均通过严格结构、覆盖、引用和引文校验；所有规格均完成离线求解。三例的标注及传播结果分别经过零 API 重放，六份结果与原保存结果逐字段一致。这里的 complete 不证明模型标注正确；010 的传播完成也没有消除其四个未决。

固定请求模型为 `deepseek-v4-flash`，服务实际返回名为 `deepseek-flash`，两者分别记录。共 3 次逻辑调用、3 次 HTTP 尝试、0 次传输重试，没有格式修复或质量补跑。服务记录的总用量为输入 37,437、输出 134,451、总计 171,888 token。

本轮最重要的方法结论是：**工程能够保存和计算数据关系，但联合标注仍会错误设定入口范围和模型可见范围，也会把明确的字段关系退化成宽计算依赖。当前三例不能整体当作语义标注正确的成功集。**

## 3. 010：完整回包观察正确，明确字段关系却被弱化

[传播审查](cases/010/propagation/report.html) · [实际标注](cases/010/annotation/report.md) · [视觉复核](cases/010/propagation/visual-review/review.md)

四个查询分支的参数分别为 term/from_date/limit、term/from_date、term/limit、term，没有补 null 或默认值。各分支的 response、total、items 身份独立，count.txt 写入和返回操作未发现跨分支错绑。记录四个分支不代表一次执行同时查询四次。

`ir_003/005/007/009` 的模型观察分别绑定完整响应 D012、D009、D007、D017。虽然此前已经定位 total、items，观察对象仍是完整回包，各回包均保留未知剩余内容；没有把字段细化当成回包裁剪。

需要保留的问题：

| 定位 | 发现 | 实际影响 |
| --- | --- | --- |
| `ir_001`；references/workflow.md:5–13 | term、from_date、limit 和两个存在性标志全部使用 compute(整份 request, derived)。明确的字段原值没有使用 select_part。 | 字段值变成 opaque 计算结果，丢失了 part_of 与原值身份。后续可能把整份 request 的宽依赖带到每个参数，降低分析精度。存在性标志可以保留计算，但明确字段应与它区分。 |
| `ir_001` | 读取及处理均假定为纯本地运行时，没有请求文件进入模型的记录或未决。 | 本地隔离依据不足，不能认为原始请求的模型观察已完整覆盖。 |
| `ir_003/005/007/009` | 外部工具调用被直接标为远程 net_send/net_receive，但源文没有独立的远程部署、网络或 URL 证据。 | 网络性质可能误标，或应保留边界未决。工具结果按 EM02 进入模型与是否经过网络是两个判断，不能互相替代依据。 |

四个 return（`ir_012/014/016/018`）的未决原因是普通返回是否面向用户无法确定，符合“不自动补造 user_output”的边界。它们保留 `events=[]`，对应 items 仍在状态和原 IR 输入中；空事件不能解释成已经证明没有任何外部返回。传播诊断保留了全部四项。

**展示说明：**当前模板统一提示“效果顺序未确定”，但这四项实际涉及效果／接收边界能否确定，没有已知步骤的排序争议。应以页面展开区的原始未决理由为准；这里明确记录该措辞不足，未修改冻结模板或原结果。

query.yaml 的两个 omit 设置已在完整源文中，也体现在 CFG 分支参数与约束里；图没有单独的配置文件读取 IR，传播中也没有相应来源。因此不能宣称审计了该文件的运行时读取。不过“应用配置”可能静态内联，传播器也不能仅凭文件引用补造一个 fs_read；这属于第一阶段抽象和执行模型应明确的边界。

## 4. 013：轮次、参数和追加正确，宽入口与完整回包观察不足

[传播审查](cases/013/propagation/report.html) · [实际标注](cases/013/annotation/report.md) · [视觉复核](cases/013/propagation/visual-review/review.md)

正确保留的部分：

- `ir_005/007` 发送 source_id（D001）和 FAST_KEY（D020）；`ir_009` 仅发送 D001，没有把密钥直接追加到 archive 参数中。
- 首次成功、重试成功、archive 成功、archive 失败的返回分别对应 result_004、result_007、result_010、result_011，没有错用首次尝试结果。
- `ir_011/013/015/017` 均为 append，实际输入是对应终态的 status。四份新文件 Data 同时保留旧文件 D002 与当次 status 的输入关系，没有把追加实现成覆盖。

需要保留的问题：

| 定位 | 发现 | 实际影响 |
| --- | --- | --- |
| `loc_ctx_source_id`、`loc_ctx_FAST_KEY`，`ir_001/003`；SKILL.md:8 | 两个输入直接登记为独立 runtime_context 键值，没有请求／环境整体、part_of 或容器读取记录，且假定本地执行。 | 当前结果只能审查两个已声明键值的流向，无法覆盖所讨论的相关容器及其他字段暴露。问题发生在入口标注，而不是求解器后来删了 Data。也不能反向编造“必定读取整个操作系统环境”，应明确相关容器的边界。 |
| `ir_005/007/009` 的最后一个 model_observe | receive 分别生成原回包 D013、D014、D010，但 observe 只绑定之后 compute 得到的 body/error/status，没有绑定原回包。 | 源文没有“工具先裁剪回包再回传模型”的规定。不能用 possible 祖先依赖冒充完整回包已经被观察；这比 010 的完整回包绑定更窄。 |
| 三次 fetch 的 body/error 操作；SKILL.md:13–14 | 原文明确要求成功 body 原值、失败 error，规格却使用 compute(response, possible)。 | 轮次身份保持了，但明确字段及原值关系没有表达，只剩可能依赖。status 编码没有被源文规定，其不透明派生可以保留边界。 |
| 三次 fetch 的网络标签 | 主要依据为工具名和获取／返回描述，没有独立部署信息。 | 与 010 一样，远程网络性质的依据不足需要保留，不能当成证明。 |

FAST_KEY 禁传诊断的声明没有被补成虚构脱敏。fast response 可能依赖请求参数，status 又依赖 response，因此可能形成 `FAST_KEY → response → status → 文件` 的间接依赖。这是保守影响链，**不能直接宣布是已证实的明文密钥泄露**。

普通 return 的处理也不稳定：010 因用户边界不明记为未决，013 则据相近的 EM06 理由确认空 effects。两者没有虚构 user_output，但对“确定无适用效果”和“缺少足够依据”的区分不一致。本报告保留实际判断，不追溯改判。

## 5. 下一步需要聚焦的标注问题

本轮已经能从错误追到具体入口位置、原子操作与观察的数据版本，不需要再猜测抽象结果是在哪一步产生的。后续改进应优先针对三个判断：

1. 相关来源容器是什么，什么依据允许只建一个字段来源；不能从 IR 的名字直接推出读取隔离。
2. 哪个版本真正进入模型或交互边界；公开输出字段不等于工具已过滤回包。
3. 明确的字段原值关系应使用字段选择，未知函数才使用宽依赖；不能用一类 opaque compute 代替两者。

这些是模型标注及执行模型解释的问题，不应通过解析理由关键词或针对 FAST_KEY、index.search 的特例规则偷偷修正。本轮未调整提示词补跑，也未提前做 DOE 判断。
