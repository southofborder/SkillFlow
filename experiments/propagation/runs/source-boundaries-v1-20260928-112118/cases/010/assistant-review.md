## 已经改善并保留的事实

**1. request.json 的整体读取与模型观察得到表达。**

`ir_001.events[0].atomic_ops[0]` 从 `storage:request.json` 取得 `data_f58214b8cc5b5…`；随后的 `events[1]` 将同一整体交付 `model_context:agent_model_context`。这发生在 `ir_003/004/005` 分别取出 term、from_date、limit 之前。

这个请求整体的 `parts_complete=false`，已识别三项字段不会抹去未知剩余；没有编造其他字段名或把范围扩大成整个环境。观察依据来自 EM03 的自然语言处理假设，不能当成实际运行抓包证据。旧结果将文件内容是否进入模型记为未决，本次在已批准的新执行模型下明确保留了这条观察。

**2. 工具返回的新内容不再被当作只从查询参数计算出的结果。**

`ir_007.events[0].atomic_ops[0]` 使用 `receive`，端点为 `tool:index.search`，事件 `effect=null`。响应 `data_44c78a9cc64e0…` 记录 `origin.acquired_from="tool:index.search"`，并分别保留各输入的 `possible` 依赖。旧结果中的响应只有 query 输入依赖、`acquired_from=null`；这次工具获取来源已补齐。

**3. 响应字段和后续用途未错绑。**

## 仍影响下一阶段分析的三个问题

### 1. 可选参数省略没有落实，核对器通过理由依赖了未定义机制

原文要求：from_date 或 limit 缺失时，省略对应调用参数，而不是传空值或默认值。旧图用四条互斥路径表达 `(term, from_date, limit)`、`(term, from_date)`、`(term, limit)`、`(term)`，每条路径一次搜索。

新图是单条线性路径。`ir_007` 除资源标识外有五个输入：

| 当前输入下标 | 内容 | 实际 Data 前缀 |
|---|---|---|
| 1 | term | `data_2bc1c452f4074…` |
| 2 | from_date 值 | `data_10f2299d0e278…` |
| 3 | from_date 存在标记 | `data_cf6f1f78a0672…` |
| 4 | limit 值 | `data_3a4c4fb469402…` |
| 5 | limit 存在标记 | `data_fa63a0e41237b…` |

缺失时省略的要求只保存在调用约束里，没有分支或受支持的条件参数绑定。核对 `finding_4` 将“value+presence+omit 约束”视为 `optional-argument` 表示；当前 `IR-PATH` 却明确不能推导未记录的可选参数执行机制。这是核对器接受了未定义机制的具体实例，不应因其状态为 `represented` 而忽略。

联合标注随后将五项全部放入 `receive.inputs`，传播也将它们全部写入响应的 `origin.inputs` 与候选依赖。程序没有读取自由文本约束、再替模型执行条件省略；传播阶段不会自动修复第一阶段的缺口。

**能确认的是：当前事实没有区分缺参情况下的实际请求组成。不能据此宣称实际工具收到了五个业务参数，更不能声称发生了五项网络发送。** 本例没有对应 `deliver/net_send` 事件；`receive.inputs` 同时承载获取依赖。存在标记本来可用于本地参数控制，但当前结构没有把这种控制用途与实际请求值区分清楚。若下一阶段把这些输入直接当成确定的外发实参，会产生误报；若直接相信约束已执行，又会掩盖表示缺口。

后续处理方向应针对通用的条件参数表示与核对规则，不补一个 index.search 专属例外。使用现有 IR 时，旧图那种各条件路径明确列出实际实参的方式可作为参照；本复核没有修改当前图。

### 2. “返回 items”仍被升级为“直接提供给终端用户”

`ir_012` 标注 `user_output`，并将 `data_6a55694bfa19a…` 交付 `user:requesting_user`。其理由是“结合用户提供请求的场景，视为向用户直接提供内容”。但原文只说 `Return the search response's items value unchanged.`；输入由用户提供，并不能证明这次函数或工作流返回直接到达用户。

items 内容身份正确，确定的用户接收边界缺少充分依据。这与旧结果是同一类问题，本次没有解决。下一阶段应区分“工作流返回值”和“已证实终端用户可见”，不能把当前用户端点当作经源文确认的事实。本例原始未决表没有记录这项边界，本复核仅在此明确指出。

### 3. 网络未知保留在审计理由里，空未决不能被读成已确认本地调用

`ir_007` 的 receive 理由明确写“网络传输未证实”“网络未知时使用工具位置”。选择 `tool` 而非臆造 `remote/net_receive` 是本次改进；它没有证明 index.search 是纯本地工具或没有网络发送。

但完整响应的 `unresolved` 为空，DOE 主文件又按约定不复制证据理由。因此下游必须按 `tool` 的定义解释为“不据此断言网络”，不能依据空未决和没有 net 标签，推导“已排除网络交互”。若需要将网络属性判为已知或未知，目前该差异仍依赖审计解释，尚未在本次未决表中明确列出。
