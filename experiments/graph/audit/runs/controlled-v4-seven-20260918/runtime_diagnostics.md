# 本轮本地记录失败与等待时间的诊断

这是助手对运行记录和代码的检查，不是模型语义核对结果。未改动生产记录器、运行输入或模型响应，也没有增加远程调用。

## 已确认的失败层次

c01、c03 均通过受控文本保真检查，在接收 HTTP 200 响应期间，将 `.transport.json.<随机UUID>.tmp` 原子替换为 `transport.json` 时发生 Windows `WinError 5`。两例都没有完整、合法的语义核对结果，不能计作模型漏检、误报或通过。

底层异常文字包含 `LLM SSE network failure`，但这是异常包装不准确：[SSE 读取实现](../../../../experiments/semantics_baseline/tools/stream_transport.py) 将网络读取与记录回调置于同一 `try`，其 `except OSError` 同时捕获了本地文件替换的 `PermissionError`。

[核对执行重试器](../../../../src/skill_ir/audit_execution.py) 优先识别了本地存储错误。两例均记录 `category=local_storage_integrity_or_interrupt`、`eligible=false`、`retry=false`，没有用再次请求模型来处理落盘问题。

## 不能从记录确认的原因

错误没有标识持有文件句柄的进程。共享冲突、权限或外部扫描都可能涉及这类错误，不能断言是编辑器、扫描程序或助手观察器造成的。

首次失败后，临时观察器改用允许读、写和删除共享的句柄；第二次失败仍发生。之后停止读取正在写入的传输文件，只读取已完成的案例记录及文件元数据。因此，普通诊断读取可能是影响因素，但不能被认定为唯一原因。

## 代码中可确认的开销机制

SSE 每约一秒执行同步检查点：重新解码全部已接收字节、计算累计摘要、拼接内容，再经记录器复制、脱敏、摘要和全量 JSON 序列化后替换文件。单次检查点成本随流长度增长，且阻塞接收线程。

检查点使用写入开始前的时间更新 `last_checkpoint`。当写入自身耗时超过间隔时，接收下一批数据后可能立即再次全量写入，放大开销。这解释了可能的接收背压机制，但本轮没有分段耗时测量，不能据此认定全部等待都来自本地记录。

## 后续最小修复方向（本轮未实施）

1. 区分本地记录异常与网络异常，保留真实失败层次。
2. 对特定 Windows 短暂访问／共享冲突，仅重试替换同一份已写好的临时文件，次数和等待有界；不触发新的 HTTP 请求。
3. 从上一次检查点完成写入后计算间隔，合并中间检查点；开始、结束、异常和完整响应仍强制保存。
4. 离线验证短暂占用恢复、持续写入失败、完整响应保存失败不重发、大流检查点频率及原始异常保留。

这些修改应使用新的源码身份和新运行目录。不能在本轮进行中改变源码，再将既有响应或失败记录冒充为新实现的运行结果。
