## 允许的表达边界

1. **结果身份可以重新编号，但不能替换来源。** `result_004` 与 `result_008` 只是此图的标识；新图可以使用别的 ID。关键是首次成功返回首次 body，重试成功返回重试 body，archive 成功或失败分别返回该次 body 或 error。名称相似不能代替定义引用核验。
2. **资源标识不是业务参数。** `archive.fetch` 的 external_resource 操作数标识被调用工具；它与 `source_id` 一起出现在 inputs 中，不等于向 archive 传了两个业务参数。`status.txt` 同样标识写入目标。
3. **判定操作可以作为源文分支的显式展开。** 检查密钥存在、工具成功、首次错误是否 transient，都是源文明示条件的图表达，不应仅因源文没有独立列出函数调用就判成无依据新增。但不能由开放操作名推导出未记录的实际错误类型枚举或判定算法。
4. **最终状态具体编码未规定。** 原图以 `success`、`failure` 记录最终类别，本次视为符合未规定格式的表达选择；不要求状态文本包含工具名、尝试编号、完整错误或响应体。也不能据此宣称源文严格指定了这两个字符串。
5. **工具响应结构未作运行契约定义。** 用两个结果表示 body 与 error，再以开放检查操作表达成功/失败，是该图的抽象表示。不能要求它凭空增加源文没有规定的状态码、空值规范、异常捕获或错误对象结构。
6. **约束声明与操作分别核验。** “返回前追加状态”需要实际追加操作和正确次序；全局约束不能弥补 c03 删除的动作。反过来，禁传声明明确保留而当前操作数也未违背时，不应要求额外虚构脱敏、清洗或拦截操作才能承认原图保留了要求。
7. **记录的控制边不等于全部路径已证明可执行。** 此图的连接没有重试回边，且成功终态没有后继抓取，这支持记录层的次数与终止分析；条件真假、工具能否返回、操作是否成功仍是未证明的执行边界。
8. **源文没有规定日志失败恢复、额外等待、额外抓取或状态写入事务。** 不应为了“让实现更可靠”增加这些步骤；同时不能把缺少未规定的失败恢复程序判为本示例漏转。
