# Static review: required failed actions and upstream input deletion

**Assessment: the narrowly stated path is supported by the frozen code, subject to the prerequisites below. This is a static hypothesis, not an executed reproduction or a finding that the current GA4 has deleted or classified an input incorrectly.** No validator, compiler, backend, model, Skill, replay, project import, or test was run for this review. Only source text was read; this new report is the only authored artifact.

Reviewed implementation identity: `3ebfb40a0053f0e3dc84aa4c7877b116445749b478b912910b8a9d192d787af6`. The ongoing run remains owned by its sole controller; this audit does not use or alter its execution state.

The relevant gap is between an action demand that has no successful operation occurrence and the deletion decision for its already processed upstream value. Identity checks and forward failure locality are present, but do not by themselves provide the missing backward demand or uncertainty edge. The correct distinction is between independent forward execution and independence from an unfinished required action.

## Preconditions for the narrow path

1. A Task demand requires an action at IR `F`, or a transfer-operation target whose occurrence cannot be found after `F` fails. The target and Task are otherwise structurally valid. `F` is not proven infeasible.
2. `F` has no successful IR/operation record. A typed `OperationExecutionError` can produce this outcome when all its evaluated paths fail. It may retain detached successful-prefix observations in the diagnostic, but those are not ordinary successful records.
3. A predecessor `P` has a successful record and supplies value `x` required by the intended action at `F`. An eligible assessment for `x` exists at `P`: for example, a successful acquisition output, or an actual upstream input use. This is not the failed IR's own input assessment.
4. No other task value/action/control demand reaches that upstream assessment. In particular, branch control retention does not independently require `x`.
5. All Task realizations are `expressed` without gaps; no unresolved Task issue, global material diagnostic, applicable review barrier, source-input mismatch, or other scoped diagnostic blocks `P`.
6. There are no declared constraint checks. More complicated constraints may block the path; this review does not claim they necessarily do or do not.
7. For an upstream CFG literal/resource operand, the explicit no-recorded-use guard must not apply. A successful acquisition output avoids that guard. A normal operand with an actual processing use can also avoid it.

Under these conditions, an upstream assessment can be labeled `deletable` even though the required failed action has not established that its input can be removed. This claim concerns the recorded input assessment; it does not assert that an automatic Skill edit occurs, that acquisition-side projection is supported, or that every DOE sink comparison becomes an excess finding.

## Separate global Task precision limit

The [initial GA4 material snapshot](source-review-input-v12-audit.json) contains 27 `retained_only`, 13 `partial`, and 9 `expressed` task realizations. **If that mapping is selected unchanged, the first 40 rows alone produce at least 40 global blocking diagnostics.** This is an initial-material conditional, not a claim about a future selected revision.

[demand_engine.py:635](../../../src/skillflow/doe/demand_engine.py:635) emits `requirement_expression_gap` whenever a realization is not `expressed` or has gaps. It passes `requirement=req` but no instruction ID or affected scope. [limitations.py:117](../../../src/skillflow/propagation/contracts/limitations.py:117) consequently treats it as global. [input_assessments.py:344](../../../src/skillflow/doe/input_assessments.py:344) does not filter that diagnostic by requirement relevance; every non-infeasible assessment enters the unresolved branch at line 374. Unresolved Task issues also emit global diagnostics at [demand_engine.py:643](../../../src/skillflow/doe/demand_engine.py:643).

Thus these residuals can currently prevent a deletion claim in GA4, but they are **a separate conservative precision limitation**, not proof that required failed-action inputs are protected correctly. Fixing Task mapping or selecting a fuller repaired annotation may remove that incidental barrier. Final online assessment must inspect the actually selected mapping, annotation, failure diagnostics and input assessments.

## Bounded follow-up, not implemented here

A future offline regression should isolate the preconditions above, then compare required failed action, genuinely independent producer, alternative successful path, and a value also required elsewhere. The semantic repair would need a distinct conservative backward requirement or uncertainty relation for demanded but unavailable actions, using their bound annotation inputs and exact fault evidence. It should not fabricate successful operation records or turn every forward-local failure into a global barrier.
