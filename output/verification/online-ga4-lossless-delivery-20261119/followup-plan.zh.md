# 本轮 GA4 之后的通用修改建议

这些建议来自 `document-guided-ga4-lossless-delivery-high-20261122-211742` 的实际材料，只是后续方案。本轮冻结实现未修改，也不授权追加线上请求、重放、Skill 执行或历史材料改写。

## 1. 先统一所有请求入口的语义协议和修订上下文

正常、纠错、完整修订和局部修订应由同一协议定义生成 schema、条件必填规则、输出封装、定位说明及只读上下文。共享编码继续负责无损表示；它不能补回调用方没有放进输入的规则。

- 局部 processing 修订必须携带正常 processing 使用的 `fragment_contract_rules('processing')`。本轮修订只有 schema，缺少 `semantic_input_requirements`、`tool_input_contract` 等条件规则；6 个改写记录因此漏掉 24 项契约。
- 携带被修订操作实际引用的 location、expression、接口定义及必要来源，标为不可修改。当前 27 个槽位没有既存 91 项 location 定义，导致模型把授权视图缺失误称为没有查询边界。优先提供真实依赖闭包；无法精确裁定闭包时，可以提供完整只读声明表，仍保留完整源文并做精确体积检查。
- 将 subject-kind 与 `affected_scope_ids` 的允许关系写入可见协议和诊断。宽 `rule/interface/output_parts` 与窄 `required/remainder` 共组时，共享影响列表会落到每个主体；本轮 6 条纠错继续失败的原因是主体分组，不是目标字段 ID。诊断应分别指出主体种类、目标 ID 和修复位置，并在同一次纠错中汇总。
- 程序生成 ID、封装和结构骨架，要求每个授权槽位有明确处理结果。可以自动处理协议明确且语义等价的表示差异；不能给缺失的必要性关系、字段绑定或证据填入语义默认值。

离线验收应同时覆盖正常与四类修复入口：必需规则都存在、只读声明能解析、Task 隔离保持、完整源文与共享值精确还原；缺契约仍须严格失败。

## 2. 修复计划同时覆盖已知校验失败和实际可表达能力

本轮初始 processing 的 ir_167、ir_311、ir_329、ir_346 在一次纠错后仍无效，且不在 27 项共享修订范围内。这四个停止点及其后继造成 34 个上一轮可处理位置失去覆盖。共享修订计划需要消费保留的校验诊断，不能只从已接受契约的源文 findings 选目标。

对 ir_167，应按真实未绑定输出与生产者关系开放必要槽位；只允许替换叶子引用，却不给缺少的生产者以表达入口，不能修好字段。对三个嵌套 cases，要求符合现行平面操作语法并保留真实控制、配对和字段关系。

CFG 修订在提交前要检查“所需修改是否在授权编辑能力内”。本轮两个 region 返回了 `{blocks: [...]}`，实际契约要求块数组，提示词没有给出完整形状；即使纠正封装，区域协议仍要求原动作完全不变，而所提 clock 拆分需要增加动作。应明确发布 Block/region schema、所有限制与有能力的编辑类型，再决定将问题交给 CFG 还是 processing。缺乏对应能力时保留具体未解决诊断，不把无效补丁当作已修复。

依赖闭包内重新构建后续材料，绑定新的审查身份；原包与新包不能混用。已验证记录和局部隔离继续保留。预算仍为七个正常阶段、两个 worker 及现有一次纠错/一次共享修订。

## 3. 把关联条件变成受支持的显式语义

本轮 ir_411–414 的四个操作消费同一 dateRange，每项产生三个备选；ir_415 按四个独立集合组合，形成 81 个数据版本。实际保存版本包含一个 helper 走 object、其余走 default 的组合，而源码对同一参数采用相同分支选择。这是过近似中的不可行路径，不是 81 份真实输入。

当前 alternatives 在合并前已没有形式化 bindings，case 条件只是文字，因此不能仅给 build 增加“同名 case 相等”规则。应增加有来源的 typed selector/guard 与分支约束，并让组合只连接相容的选择；不同来源或确实独立的条件仍保持独立。未知值、未知地址和资源版本的身份规则继续保留。

同一机制应核验 fulfilled/rejected 包装：ir_457/459 的成功后继仍包含失败包装，因此读取 value 出现 missing_part。不要用全局吞错、虚构 value 或移除分支来掩盖它。

离线样例需要覆盖共享条件、独立条件、默认时钟差异、异常包装、成员配对、数量/存在性，以及 FIFO/LIFO 一致性。

## 4. 先核实敏感源和调用接收方，再解释 DOE 候选

本轮 102 项重复的句柄创建凭据声明中，有前向记录的 100 项都定位到同一个 opaque live-environment 数据节点。site/default-range 的不透明计算也使用该节点，敏感性引擎据 possible 依赖传播并扩大为整个输出。加上数据版本展开，形成 109,448 条敏感性推导和 83,442 个不同候选。这些是可能影响关系，不能描述成真实明文凭据泄露。

先对照源文核验每项敏感声明的真实读取位置、字段路径、创建结果及缓存资源身份。这 102 项声明的定位对象是 creation_env/creation_sc_env/creation_ix_env 的字段，不是句柄内部字段；应检查它们与源码环境值及解析结构的对应关系，不能只按凭据标签判断位置。源文已有确定选字段/构造表达式时应忠实表达。核验 13 个远端接收方遗漏及 8 个响应投影关系不足的位置，保留实际调用、请求/响应、缓存版本和接收方依赖。

`demand_transfer` 是反向必要性契约，不能直接用来抹除实际正向读取、观察或可能传播记录。若需要更精确的语义影响视图，应单独绑定已审查关系并给出依据，原始事实仍保留。不同声明 ID 或不同资源不能仅因标签相同就合并。

## 5. 避免报告反复展开共享证据

本轮 DOE JSON 约 266 MB，HTML 3,938,066,348 字节，Markdown 3,697,695,105 字节。候选 ID 不重复，但报告在每个候选下反复展开关联证据、需求和限制，造成体积与内存压力。

采用共享证据索引和稳定引用：总览、按 sink/操作分组、完整候选索引及证据明细相互链接；每个候选仍可追到原始材料。HTML 可以分页或按需展开，Markdown 使用独立索引页与共享附件。原始 JSON、语义结论、审查范围和来源不裁剪；展示去重不改变候选语义。原子写入改为流式生成，避免同时构造数 GB 字符串。

对这种多分支、多声明输入做离线规模回归，分别记录候选数、输出字节、计算/发布时间及明确的内存测量。先消除不可行分支、校准种子证据，再评估剩余的合理规模；不能通过删除候选来隐藏语义问题。

## 后续顺序

先完成共享协议、只读上下文与修订能力检查，再处理分支关联、敏感源/接收方语义和报告发布。保留本轮失败、实际成本及历史来源。全部离线验证通过后，另行获得新的线上授权；本轮的唯一启动和唯一重放额度不复用。
