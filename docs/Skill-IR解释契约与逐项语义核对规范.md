# Skill-IR 解释契约与逐项语义核对规范

本规范对应核对协议 v5。运行时权威规则位于 `skill_ir.semantic_contract`，规则版本为 `skill-ir-semantic-contract-v4`。核对提示词、反馈说明和报告引用同一份带编号的规则；运行记录绑定其版本及 SHA-256。本轮仅更新核对解释与响应，生产提取 Prompt 不改，保留原 IR Schema、结构校验及 Lean 打印器。所有核对字段都保存在图外，不给原图 IR 增加字段。

## 1. 核对目标

唯一核对流程为：冻结 CFG → Lean 生成并核验受控文本 → 模型一次比较完整原文与受控文本 → 程序校验证据、定位并生成反馈。

核对对象是明确要求及其关系，不是整体文字相似度。原文明确规定的动作、对象、条件、次数、顺序、返回要求和禁止事项严格核对。会改变数据内容、去向或执行条件的明确步骤应分别可定位。例如“遮蔽后发送”应能找到遮蔽操作、发送操作及相应数据和先后关系；标题或约束中的“安全处理”不能替代这些事实。

数据依赖优先精确表示；不能进一步区分时，可以按固定规则接受有证据的保守候选。此种精度不足正常保守表示。保守表示不适用于添加业务动作、额外控制路径、修改执行条件或放宽禁止事项。

`audit_passed` 表示在本轮契约下，核对模型没有报告尚存的明确差异，且核对已完成。允许含有明确说明的保守依赖；这不等于源文与 CFG 严格语义等价，也不保证模型找全了要求。模型判断要求的含义、合理抽象、语义覆盖及差异，程序检查格式、材料身份、真实引文、定位和保真；不靠关键词规则代替语义判断。

## 2. IR 的既有含义

- `literal` 保存字面值；`context_key` 标识已声明的运行时入口；`result` 引用某条操作实际定义的结果；`external_resource` 标识文件、工具、API 或服务。资源标识不等于资源内容，也不自动是业务参数或网络端点。
- 结果按实际 identifier 关联定义。两次调用的名称相似不意味着结果可互换；`semantic_name`、块名称、draft ID 不能替代引用绑定。
- `dispatch` 与 `return` 是固定控制终结操作，均不产生结果。前者由出边连接后继，其输入记录分支判断依赖；后者结束当前路径，其输入记录返回内容。`return` 不自动表示向用户展示数据。
- 开放业务操作的含义结合其明确文字、操作数和源文判断，不用操作名猜测未记录的内部实现。既有提取契约中的代码黑盒边界继续有效：核对显式接口、输入输出和外部副作用，不要求展开源码内部循环与局部变量。
- 图、块、操作三级约束分别是相应作用域的声明。声明某动作不等于该动作已存在；声明禁止某行为也不证明运行时一定遵守。声明与操作的冲突可以被受控文本忠实展示。
- 输入、输出、操作次序和控制边按实际记录解释。合流后的操作允许引用不同分支产生的结果；多输入列表本身不证明所有值同时可用，也不提供隐含的精确选值或 `phi` 执行保证。
- 结构校验检查定义、引用、连接等结构条件，不证明每条路径可执行、循环终止、文件写入成功或所有输入在每条路径均可用。受控文本往返证明只保证明确记录得到保持。

新增的 `IR-SOURCE` 规则将来源入口与取得的值分开解释。例如，原文“从请求取得 city”可以记录为获取操作输入 `context_key=request`、输出为 city 对应的 `result`；操作名及明确约束保留取值目标。入口指出来自哪里，不自动断言读取了请求整体，也不证明模型观察了请求整体。不能把容器入口误报为新增业务行为，也不能仅因输出名包含 city 就认为请求来源已得到保留。

| 原文关系 | 第一阶段提取与核对应保留的事实 |
|---|---|
| 从某个容器取得字段，未说明具体读取机制 | 来源入口、取值目标、实际输出及其后续参数绑定；不植入宽读或观察步骤 |
| 明确的仅取单键接口、局部读取或隔离机制 | 实际接口与限制；不能统一改成整体读取 |
| 明确先读整体，再选取字段 | 两个可区分动作及其中间结果；后续引用实际选取结果 |
| 检索工具或外部集合返回新内容 | 内容获取边界及请求参数；请求影响响应不等于响应完全由请求构成 |
| 明确的纯函数工具 | 从已有输入计算的关系；不能因为称作工具就新增外部来源 |

第二阶段联合标注才根据完整源文、当前图与固定执行模型分别表达读取范围、模型观察和明确取值。核对器不读取该阶段标注或传播结果，不要求将其中的执行假设反向补造成源文 CFG 动作。缺失原文明示的来源仍是可核对的遗漏，不能以 `DEP-SOURCE` 降格处理；实际参数、禁传限制及返回身份也不因来源范围扩大而改变。

## 3. 七类阅读检查点

| 提示标识 | 中文名称 | 阅读时关注的关系 |
|---|---|---|
| `normative_scope` | 要求性质与作用域 | 实际要求、条件性要求、示例和背景；必须、允许、禁止；主体和适用范围 |
| `actions_objects` | 动作与对象 | 动作是否存在，操作对象、工具和资源是否一致；明确处理步骤是否分别可定位 |
| `data_bindings` | 数据来源与绑定 | 获取来源、参数用途、调用结果身份、返回绑定和原样保留要求 |
| `guards_exceptions` | 条件与例外 | 触发或禁止条件作用于哪个动作；缺省、失败、回退与例外关系 |
| `order_dependencies` | 顺序与依赖 | 先后关系、结果使用关系、返回前动作及其适用出口 |
| `counts_termination` | 次数与终止 | 恰好、至多、至少、重试对象和次数、停止条件及终态 |
| `grounding_consistency` | 反向依据与一致性 | 图中业务动作、参数、条件和限制是否有源文依据；操作是否与声明冲突 |

这些检查点只用于提示模型阅读，不是响应分类字段，不要求七类各填一张表，也不规定一个业务项只能属于一类。允许将关联的行为、条件和结果合并核对。例如“首次暂时失败才重试一次，重试成功原样返回该次响应”可以合并说明，但必须判断触发条件、次数与返回身份，不能只因“有重试和返回”就判整体保留。

局部存在差异时明确指出保留了什么、错了什么，不能用整项 `represented` 掩盖局部错误；需要分别表达不同结论时合理拆分。模型在同一次核对中检查结论是否与所引证据和其他发现冲突，不增加要求提取或第二裁判调用。原文索引仅用于定位，不是人工要求表。原文与受控单元仍要求定位覆盖，但全部编号被引用不证明语义已穷尽。

原文本身明示危险行为时，应忠实核对该行为是否建图。本阶段不判断恶意、风险、必要性或 DOE，也不依据第二阶段执行假设自行补造宽读取或模型观察操作。

以下为人工规格示范，不是模型实测结果，也不进入模型核对输入。每行只改变一个关键关系，动作词相似仍可能不满足要求：

| 类别 | 源文要求 | 反例表示 | 应指出的差异 |
|---|---|---|---|
| 要求性质与作用域 | 整个流程都不得把令牌写入诊断输出 | 禁传声明只约束主工具块，回退诊断没有相应限制 | 全局禁止范围被缩小 |
| 动作与对象 | 先遮蔽日志中的令牌，再发送日志 | 只有发送操作，标题写“隐私保护” | 实际遮蔽步骤缺失，标题不能补造 |
| 数据来源与绑定 | 重试成功，返回这次重试的响应 | 返回操作明确引用首次调用结果 | 调用结果身份错绑 |
| 条件与例外 | 首次暂时性失败时才允许重试 | 所有首次失败均进入重试 | 重试条件被扩大 |
| 顺序与依赖 | 每个成功或失败出口返回前追加最终状态 | 状态追加只出现在成功出口 | 失败出口缺少必需的前置动作 |
| 次数与终止 | 失败后最多再试一次 | 第二次失败又回到重试调用 | 增加第三次及后续尝试 |
| 反向依据与一致性 | 获取内容后直接返回，没有等待要求 | 多出明确的两秒等待操作 | 新增无依据的业务等待 |

表中比较遵循既有抽象层：不要求把脚本内部算法拆成上述节点；若自然语言明确要求一个独立处理步骤，则不能用脚本或操作的泛化名字替代该步骤的可定位表示。相反，单纯保存的示例代码不能在没有运行依据时变成新增执行路径。

## 4. 保守依赖的边界

保守规则只接受图中已有、且有源文和控制关系依据的候选来源，具体编号与文本以运行时契约为准：

- `DEP-MERGE`：保留合流或不同路径上的候选结果；不能据此宣称每个结果都在本次路径产生或同时传入。
- `DEP-SOURCE`：保留当前表示无法进一步区分的合理来源候选；不能凭空增加读取对象、发送目的地或来源操作。

保守核对项必须提供已有候选事实编号、适用规则、理由和丢失的区分。程序检查编号、引用及其定位类别，不证明模型关于候选集合完整性的判断正确。

以下对照必须保持：

| 表示 | 判断边界 |
|---|---|
| 分支 A/B 产生 a/b，合流记录两者为候选依赖 | 可按保守规则接受；保留两者与路径的证据，不声称同时使用 |
| 操作明确要求同时向工具传 a 和 b，而原文只允许 a | 仍须报告额外参数；不能降格成候选关系 |
| 重试成功后明确返回首次结果 | 仍是错误绑定；不能以“结果可能来自两次调用”掩盖 |
| 缺少原文要求读取的来源 | 仍须核对遗漏；空候选或其他来源不能代替 |
| 原文禁止传密钥，图中实际调用输入包含密钥 | 仍须核对禁传与调用的冲突；保守规则不放宽禁止事项 |

保守表示不修改 CFG。核对产物中的候选是表示精度说明，不是已经执行二次传播后的数据集合。后续阶段必须把候选理解为可能性，不能把每个候选成员当成必定读取或必定传递。

## 5. v5 结果契约及反馈

正常结果使用 `outcome="completed"`，五类判定为 `represented、omitted、mistranslated、unsupported_addition、internal_conflict`。每项保存源文要求、实际表示、理由、双方证据及建议；相关要求可合并，局部差异必须指出。背景项不能替代业务通过。

`conservative` 仍可省略或为 null；明确采用保守依赖规则时，保存规则、候选事实、损失区分和理由。程序校验候选定位和结果身份，不证明候选业务合理性。`representation_summary` 只列保留项和其中明确采用保守说明的项，未填写说明不代表精确。

v5 删除 `unknown、unknown_reason`。遇到妨碍必要判断的具体冲突、缺失材料或实际表示能力限制，返回独立分支：

```json
{
  "schema_version": 5,
  "contract_version": "skill-ir-semantic-contract-v4",
  "outcome": "cannot_assess",
  "failure": {
    "reason": "具体阻碍必要判断的原因",
    "source_refs": [],
    "controlled_refs": [{"unit_id": "必须为现有编号", "quote": null}]
  }
}
```

至少一侧必须有真实定位，源文引文及已给出的受控引文均校验。失败分支不携带 findings、覆盖数组或 notes；完成分支不允许 failure。程序校验后保存为 `semantic_failure`，与传输和格式错误分开，不自动修复，也不冒充没有问题。程序并未证明失败理由的语义正确性。

未展开内容、普通不透明行为、有依据的候选关系，以及原文未保证运行成功，本身不妨碍忠实表示，不能仅因此失败。源文可保留的开放描述继续正常核对。

反馈只针对四类明确差异；合法保守项不要求重提取。只有完成响应、真实证据与覆盖有效、至少一个业务项且全部保留时，才可 `audit_passed`。全背景项停止为 `semantic_failure`。坏 JSON、非法定位、错误引文和缺失覆盖保持执行错误，不静默修补。

## 6. 实验、重放和验收

新版运行必须使用新目录。运行身份绑定源包、实际图、受控文本、契约及源码摘要；旧版输入、响应和报告保留，新版不自动迁移或重新解释旧结论。

以下七例安排是核对协议 v4 首次落地时的历史实验身份，保留其原始输入、响应和结论，不改写为解释契约 v4／核对 v5 的实测：F01 原图及四反例，以及暂停批次 `full-pipeline-20260917` 中 001、010 的第 0 轮实际图和同轮冻结源包。每例使用完整独立上下文，一次逻辑核对，不进行语义修图，不重启 30 例全流程。

请求官方 DeepSeek 的 `deepseek-v4-flash`。默认超时为 600 秒，实际 urllib/SSE 配置是连接和阻塞读取等待上限，不是总生成时限。复用最多两次额外核对执行重试；只有明确结束的暂态传输错误可重试，完整响应中的坏 JSON、合法语义失败或语义差异不重试。不确定或用户中断的请求不自动重发。HTTP 尝试单独计数。

离线 `replay` 不创建在线客户端，重新解析、核验和生成报告。保存响应不得因源码变化被冒充为新版实测。

工程验收包括可组合语义项、可选说明和严格证据契约，反馈门槛，输入隔离，重试、中断、恢复和离线重放，30 个固定图及 F01 反例往返校验，以及既有相关回归。旧版运行明确拒绝，不自动删字段或补 null 后重新接受。形式化证明继续限定于受控文本保持图事实，不新增关于模型语义判断的证明主张。

方法验收逐例检查误解是否消除、明确缺陷是否仍被发现，以及是否误把真实错误宽进。外置预期只在模型核对结束后使用；自动匹配仅生成复核候选，助手复核与用户确认分开标注。七例不能支持泛化或统计显著性结论。

历史解释契约 v3 的诊断范围另存 `experiments/propagation/runs/source-boundaries-v1-<时间戳>/`：001、010、013 从冻结源包重新提取，进入既有有界反馈，再对选定图进行联合标注和离线传播。它不覆盖上述历史七例，也不将最新一轮结构有效图自动称为语义核对通过图。报告按来源、读取范围、观察版本、取得值和实际接收方复核完整链路，不因后续传播完成而更改核对停止状态。

本轮解释契约 v4 只对当前 001、010、013 既有 CFG 做新版单次核对，使用 `max_semantic_revisions=0`，不重新提取。结果与第二阶段标注的一次修复分别保存，二者不互相提供判定答案。
