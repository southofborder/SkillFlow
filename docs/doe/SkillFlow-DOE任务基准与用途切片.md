# SkillFlow DOE 任务基准与用途切片

## 当前实现更新（2026-10-15）

[Task v3](task-evidence.md) 将任务基准从联合标注中分离：只接收完整冻结源文和可选用户任务，逐非空物理行记录处置；Task 是唯一要求释义，保留精确原值、条件、次数、顺序、范围、质量、副作用、禁止及同元素关系。Task 不包含 CFG bindings，程序封存来源、独立请求和任务版本。

固定 Task 后，标注阶段逐 requirement 输出 `expressed / partial / retained_only / unmapped` 的 realization、图绑定和剩余缺口，并声明六类正向保持目标。`constraint / prohibit` 不再是正向 goal。完整源文、Task、逐 seed demand 及处理关系由[四轴审查](joint-pipeline.md)独立检查；Task 问题触发 source-only 修订和全新标注，不能让当前载荷反向扩大基准。

程序生成“原文 → Task → realization／缺口 → 原始 demand → 编译 goal → 逐 seed 推导 → sink”对应。现阶段未知影响范围的未表达限制保守全局处理，不凭模型任意绑定宣称局部；有条件的诊断计算不能升级为支持缩减的结论。后端完成、真实引用、登记覆盖及审查通过均不构成自然语言完整性、行为满足或无 DOE 证明。

下面的任务依据、功能保持及 sink 回溯／用途原则继续有效；早期 `Task` 草图、原文编号和最终 DOE 模型分工属于历史接口。当前结构以[独立 Task](task-evidence.md)、[反向需求](backward-demand.md)、[敏感范围对照](sensitivity.md)和[正式分析链](joint-pipeline.md)为准。说明与报告使用中文，模型指令正文使用英文。历史输入及传播事实不回写。

确认日期：2026-10-10。本文固定 DOE 阶段的任务依据和 sink 审查材料选择原则，是后续实现与验收的设计基准。

**Historical design below:** the original `Task` sketch and final-model allocation have been superseded by the Task, demand and sensitivity contracts linked above. The read-only `SinkSlice` service remains available. Existing CFG, Data, propagation facts and historical results are not rewritten.

## 1. 两个概念与必要性判断

任务基准回答：**减少暴露以后，哪些事情仍然必须做到？**用途上下文回答：**这个接收方取得这份信息之后，用它做什么？**

两者共同支持必要性判断，但都不能把“当前流程使用了某数据”当成“该数据必要”。审查对象是具体 sink 阶段、接收边界和该阶段实际绑定的 Data、字段或信息范围。动作必要性不作为 sink 准入条件；不必要动作的敏感暴露和必要动作中的额外敏感载荷都要检查。

### 1.1 任务基准是功能保持的参照

例如，一项任务要求给符合条件的记录发送通知，接收者取 `recipient`，正文保持 `summary` 原值，最后保存处理条数。一种实现读取整条记录，再从中取得这些字段。

DOE 需要保持上述结果与限制，却不必保持“整条记录全部进入模型”这种内容可见范围。

| 错误做法 | 后果 |
|---|---|
| 把当前发送的每个字段都列为任务要求 | 额外载荷会被循环证明为必要 |
| 只保留“完成通知”这一句目标 | 可能错误建议改写 `summary`、忽略订阅条件或删除计数要求 |

采用数据最小化的基本思想：**减少提供的信息，同时保持所需功能。**所需功能必须依据任务要求确定，不能由当前暴露范围反向定义。[Data Minimisation: a Language-Based Approach，§4.2](https://arxiv.org/html/1611.05642v1#S4.SS2)

该论文的功能保持条件不直接构成自然语言 Skill 的证明。SkillFlow 不把当前所有外发字节不变作为目标，不宣称已经求出任意任务的全局最优最小化方案。

### 1.2 用途上下文是相关使用事实

向后回溯能够说明模型观察的数据来自 `events.json`，但还不能说明它为何需要这些内容。还应保留相关使用：

```text
观察 events
    → 检查 opted_out、urgent、value
    → 取得同一记录的 recipient、summary
    → 发送通知
```

这些事实使判定器能够区分筛选需要哪些字段、发送需要哪些参数、`access_token` 是否参与任务要求的功能，以及整体观察是否存在可以减少的范围。

**下游操作是判断材料，不是必要性的证明。**即使程序发现某字段被使用，模型仍须判断该使用是否服务于任务，还是过量实现自行制造的需求。

通知、提交和持久保存也可能本身就是任务结果。没有公开输出、没有本地后续消费者，或图中没有后续读取，都不能直接证明它们无用。

## 2. 任务基准 `Task`

### 2.1 依据的默认与边界

采用已经确认的规则：

> 有独立用户任务时，以用户任务为目的依据；没有时，自动分析 Skill 声明的用途，并将结论明确限定为“相对该 Skill 声明用途的静态最小化判断”。

不要求逐个 Skill 额外填写任务，也不把 Skill 作者声明的用途视为已经获得真实用户授权。

用户任务与 Skill 的要求存在冲突时，保留并说明冲突以及本次采用的目的依据，不静默改写输入。无法据此完成必要性判断时明确记录判断失败，不能用空发现生成安全结论。

### 2.2 最小职责结构

```text
TaskBasis
├─ basis
│  └─ user_request / declared_skill
│     本次采用的目的依据，由程序确定
├─ purpose
│  └─ 要实现的结果、服务对象及原文编号
└─ requirements[]
   └─ 必须保持的结果、条件、副作用、质量及禁止事项
      每项引用已有原文编号
```

`purpose` 和 `requirements` 的说明都须具有可定位的依据，不能根据当前载荷倒推任务需要什么。相关要求允许合并表达，不强制逐句原子化，不增加维度分类和评分，也不另建一条重复的证据链。

程序确定依据身份并提供原文；同一次 DOE 判断解释目的、需要保持的要求和敏感范围。不增加独立的任务提取模型角色或调用。

`Task` 保存于 DOE 自己的阶段结果，不写入 CFG、Security Profile 或冻结传播事实。它不是提前填写的必要性答案，不用于筛掉任何 sink。

### 2.3 保留要求，不豁免全部载荷

源文明示的结果身份、数据来源、条件、次数、必要副作用、质量和禁止事项默认保留；但某项功能存在，不会使其全部实现载荷、可见范围和留存范围自动成为必要。

| 样例 | 默认必须保留的要求 | 不能由此推导出的必要性 |
|---|---|---|
| 001 | 通知条件；`opted_out` 限制不被 `urgent` 豁免；每条选中记录发送一次；同元素 `recipient`／`summary` 配对；`summary` 原值；未选中不发送；禁传 `access_token`；保存处理条数 | 模型必须观察整条记录；计数文件需要附带记录正文或凭据 |
| 010 | 查询一次；`term` 原值；可选参数存在时传原值、缺失时省略；返回 `items` 原值；保存 `total`；禁止删除索引；不自行增加模糊扩展、校验或规范化 | 存在性旗标属于请求载荷；整份请求必须交付工具；模型需要观察响应的全部未知内容 |
| 013 | 凭据存在性分支；首次瞬态失败才重试且只重试一次；规定的回退；archive 至多一次且仅传 `source_id`；正确返回该次成功响应的 `body` 原值或 archive 的错误；成功后停止获取；禁传 `FAST_KEY` 到 archive 和诊断输出；所有终态前追加最终状态 | 模型必须观察整个环境；状态文件需要凭据或完整响应；首次、重试、回退响应可以互换 |

001 的 `count.txt` 和 013 的状态追加是明确的辅助功能，不能仅因“看起来辅助”就删除。保留计数或状态这一要求，同时审查是否保存了额外敏感内容。

三例的解释还须保留这些限定：

- 001 的选中条件是 `opted_out` 不为 true，且 `urgent` 为 true 或 `value >= 100`；不生成摘要、不改写正文、不增加额外格式转换。“处理条数”不能自行改成读取条数或总记录数。源文的 `access_token` 禁传要求按其原文范围引用，模型观察及其他边界的必要性另按 DOE 规则审查，不假称源文已经定义所有分析边界。
- 010 的完整任务由 `SKILL.md`、`references/workflow.md` 和 `query.yaml` 共同提供。工具支持模糊匹配是能力说明，不是本任务要求；参数格式说明不构成预调用校验指令。
- 013 的“最终状态”没有规定新的记录格式，也不授权保存整份响应或凭据；archive 失败后不重试。首次、重试和回退的输出不能仅因名称相近而合并。

第一版允许提出字段缩减、限定回传或明确局部处理建议，但须说明如何继续满足要求。新增机制必须标为建议，不能被写成当前事实中已经存在的保护。没有找到缩减方案，不证明现有范围全局必要。

## 3. 用途切片 `SinkSlice`

### 3.1 一份业务输入，两侧关联事实

通过公共 `load_propagation_materials()` 取得经过校验的阶段材料。传播只保存自己的 Data、记录和实际 sink，源文、CFG 和编译映射通过上游引用取得；不保存独立的切片总包。精确反向需求使用已核验编译映射，不能仅凭用途关联反猜观察关系。

```text
SinkSlice
├─ sink
│  └─ 当前操作、阶段、接收边界和实际载荷
├─ backward_slice
│  └─ 内容来源、字段关系、处理过程和数据版本
├─ usage_context
│  └─ 当前动作及相关生产／消费操作
└─ context
   └─ 条件、先后关系、逐元素配对、约束和诊断
```

源文、相关 IR、Data 和操作存入共享索引；各切片引用原编号，不为每个 sink 复制整份对象。完整可读源文作为公共材料提供一次，避免局部摘录遗漏全局禁止项；不发送全部 IN／OUT、无关 Data 和运行日志。

`backward_slice` 解释本次载荷来自哪里、经历过什么；`usage_context` 提供相关处理和消费事实。两者可以引用同一个操作，共享索引只保存一次，不是两套独立数据流。

完整事实文件继续承担审计职责。切片不能通过静默截断来源、版本或候选来控制输入规模。

### 3.2 程序生成事实关联，模型判断用途

程序使用实际操作的输入／输出、CFG 结果定义引用和位置变化建立内部使用索引。普通操作沿用 IR／事件／操作坐标，逐元素 body 同时保留实例的元素身份及 body 坐标。

不按名称相似性、opcode 名称或理由关键词推断用途，不解析 `origin.at` 字符串猜测操作位置。`origin` 用于保留来源、内容和依赖关系，不能替代实际记录的操作关联。

不同 sink 的用途上下文固定如下：

| Sink 情形 | 必须保留的用途关联 |
|---|---|
| 模型观察 | 同一 IR 中在已保留次序下可能消费该版本的处理；公开结果的后续消费者；观察的是处理后结果时，保留生成该结果的相关操作 |
| 网络／工具／用户交付 | 当前调用、接收边界、实际参数、约束和任务要求；已有请求／返回关联可保留，不猜测接收方内部实现 |
| 文件／上下文保存 | 本次保存载荷、写入后的版本和已有图中对应的后续读取；保存本身的源文用途始终保留 |

沿明确的结果和数据使用关系，经相关内容处理和原样结果引用，继续追踪到 return 或交付／保存边界。到达外部边界后，不擅自展开其内部处理；没有公开输出不证明交付无用。

普通 return 即使没有传播 events，也必须根据 CFG 输入保留返回身份。不能为它虚构公开输出或用户交付。

### 3.3 保存与读取的版本关联

从本次写入的实际位置变化及写后版本关联后续读取，不仅凭文件名或位置名称建立使用关系。

- 确定覆盖或删除结束旧写入的定义关联；不删除历史 Data 或早先观察。
- 弱更新、可能别名和部分顺序保留适用的候选关联。
- 追加的 sink 载荷是本次追加输入；它与文件旧内容、追加后的存储版本分别处理。
- 未找到后续读取，只表示当前 CFG 没有建模该读取，不能直接判保存无用。持久保存可能是任务结果，仍须结合源文用途判断。

### 3.4 切片必须保持的关系

1. 从实际载荷槽位出发，不把整个入口状态当成当前动作使用的数据。复用现有载荷／控制槽分离规则，存在性旗标作为条件保留，不成为参数明文。
2. 选中字段回溯到父整体，只用于解释来源和范围，不能重新扩大字段载荷。未知剩余保持未知，不编造其他字段或凭据。
3. 组成、选取、排除、覆盖、`derived` 和 `possible` 分开保留。粗粒度输入依赖不能复活已排除的旧字段；可能影响也不等于全部明文包含。
4. 不同阶段、数据版本和接收方分别保留；后续清理不能撤销早先观察。
5. `recipient` 与 body 保留同一元素实例，不分别汇合后重新配对。筛选保留成员内容关系，不伪造真实集合长度或执行次数。
6. 相关 CFG 条件保留为条件子图，不枚举全部路径，不把不同分支条件写成必然同时成立的合取。固定／部分顺序及必要因果保持原意。
7. 获取返回同时保留其获取边界和适用请求依赖。请求影响响应不证明响应包含请求凭据；原值返回与计算结果不能混同。
8. 所有用途关联仅表示已有事实中的静态使用可能性，不自动推出必要性。切片生成完成不证明路径真实执行、模型推断正确或不存在 DOE。

原值保持的数据流与派生影响应区别处理，这与成熟污点工程的划分一致；必要性仍需结合任务语义判断。[CodeQL 数据流说明](https://codeql.github.com/docs/writing-codeql-queries/about-data-flow-analysis/#normal-data-flow-vs-taint-tracking)

## 4. DOE 判断与程序检查的分工

程序提供可定位、可核验的关联事实；同一次 DOE 判断解释任务、敏感性、边界用途、所需范围和缩减依据。不增加一个“下游使用即必要”的规则，也不以消费者数量、边界等级或存在传播路径代替语义判断。

每项最小化建议须说明减少什么、修改哪里、对应哪些任务要求，以及为什么必要功能仍可保留。新增机制属于建议，不是现有事实；静态解释不能冒充实际执行验证或任意函数等价证明。

普通 opaque 内容、契约默认观察和 `possible` 依赖继续分析，不恢复泛化的人工未决出口。真实引用缺失、目标冲突或能力限制使判断无法完成时，明确记录失败；失败不能被空发现或“安全”结论掩盖。

DOE 结果独立保存。敏感性依据来自一次联合标注的声明，不回写冻结传播 Data；不把判断证据链加入本次传播主文件。模型提示词的指令正文继续使用英文，解释与报告使用中文。

## 5. 验收场景与当前状态

以下用例是现行算法的验收要求；实际模型表现与离线工程验收分别报告：

| 场景 | 验收要求 |
|---|---|
| 001 通知与计数 | 保留条件、同元素配对、`summary` 原值、禁传和计数要求；整体观察不能自动被判为必要 |
| 010 可选参数 | 保留参数原值和缺失时省略；存在性旗标仅作为控制，不进入交付载荷 |
| 013 获取与回退 | 各次响应与返回身份不串联；保留禁传、重试／回退和终态状态要求；环境整体不等同于必要字段 |
| 普通 return 无 events | 从 CFG 保留返回身份和用途，不判无用，不虚构输出或调用者边界 |
| 保存后无读取 | 保留源文中的保存用途，不因缺少本地消费者而判保存无用 |
| 保存后确定覆盖／删除 | 后续新值读取不错误关联旧写入；弱更新和部分顺序保留候选 |
| 清理前后两次观察 | 分别绑定当时版本，后续结果不替换早先原数据观察 |
| 逐元素及条件操作 | 配对、控制槽和必要先后关系不因切片而丢失，不声称候选同时发生 |
| 脱离审计目录 | 公共加载器通过组件及明确上游引用取得基础事实和编译映射；缺失上游明确失败 |
| 缩减与功能保持 | 建议引用任务要求并说明保留依据；找不到缩减不宣称已证明全局必要 |
| 冲突与真实失败 | 保存冲突及采用的目的依据；不能把无法完成判断当作没有 DOE |
