# Sink 载荷需求绑定与三例验收

本规范补充[正式分析链](joint-pipeline.md)，沿用独立 Task v3、固定 Task 的标注、四轴审查及逐 seed 推导。不新增业务字段，不修改前向传播、反向规则或敏感性结论种类。

## 按任务规定的功能终点保持信息

Task 明确规定交付参数时，需求应落到该次 `deliver` 的实际输入槽位，并保持规定的字段、原值、条件、版本及同元素关系。只在上游字段选取输出或构造输入建立需求，不证明接收边界已表达完整。

Task 明确规定保存内容时，保存行为与本次写入内容分别保持。`write` 的 action seed 不代替载荷的 value 或其他规定性质；追加只指本次追加内容，不能将旧文件整体变成任务需求。删除没有保存内容需求。

Task 仅要求动作、没有规定某份载荷时，不能擅自把实际全部输入升级为任务要求。真正的全值要求、不透明处理引出的保守输入需求、普通 return 的真实输入及其明确字段关系继续成立。受支持的反向推导已经建立同一要求在边界的内容需求时，不再添加同义 seed，也不强制重复 `expected`。

接收方内容需求仍由该边界的真实操作输入确定，不能按 Data ID 相同自动合并。`receive` 反传的整请求保守保留与 Task 明确指定的参数需求是不同依据；前者不能作为后者已经精确表达的证明。

## 审查遗漏而不只审查已有 seed

`requirement_checks` 从原文和已封存 Task 核对全部适用功能终点，包括原候选根本没有生成的载荷 seed。Task 正确、标注遗漏时使用既有 `domain=annotation`，定位 realization 或相关操作父容器，进入固定 Task 的标注修复。Task 本身遗漏或误读时使用现有隔离修订路径，不向 Task 修订器注入接收方、当前载荷或审查自由文本。

`declaration_checks` 继续检查已有 seed 的目标、性质、范围、版本、条件和接收方。四轴登记完整、结构上存在一个 action seed，都不能证明复合义务已经完整表达。结构程序不从自然语言关键词判断“必须有载荷需求”，也不自动补 seed。

教学与回归使用独立合成的字段交付、结果保存和条件参数场景；同时保留正确 return、纯动作、真实全值和 opaque 保守关系的正例。模拟审查仅验证协议、路由和计算，不提供真实模型检出率。

## 三例在线验收

三例重新提取 Task，不导入修改前的 Task 或候选。对照按源文义务、动作和信息关系进行，不要求 requirement、Data 或 seed ID 跨运行相同。

- 001：同元素 recipient／summary 原值需求是否到达工具输入；模型筛选需求不能扩大为工具参数。
- 010：原参数及可选加入／省略条件是否到达请求输入；不能用外部获取反传的保守整请求需求替代精确参数依据。
- 013：每个终态的最终状态是否同时有保存行为和本次追加内容的保持需求；不能把 `possible` 影响当作凭据明文。

已有 gap 和未支持限制仍按当前全局 blocking 规则保留，没有新增可信的局部影响证明。候选过量减少，可能来自保守限制，而不是需求绑定修复；验收必须追踪原文 → requirement → realization／gap → raw demand → compiled goal → seed 推导 → sink 输入。

三例调度使用 pilot v6，委托原有 pipeline v6。正常每例三次语义调用，仅标注修复五次，Task 修订六次；两条路径共用一次语义修复预算。结构纠正不限次数，HTTP 重试另计，不把十八次语义调用称为全部请求上限。源码和实际 Prompt 在在线运行前冻结，已有接受响应不重发，运行结束后零 API 重放。

统计只属于实验审计，不进入模型业务输入。六阶段逐调用记录输入、输出和推理 token；推理／缓存明细不重复相加，缺失 usage 记未知。请求耗时、整例和整体耗时分别记录，重放不改写在线耗时。报告链接既有 Task、审查、推导和 DOE 页面，不再复制一套事实。

离线命令、真实运行、失败及逐例复核记录另附验收结果；这里的规则本身不构成要求完整、需求最小或无 DOE 的证明。
