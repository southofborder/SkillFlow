# 按槽修订与字段级审查

修订沿用每个阶段现有的顶层 JSON、记录 ID 与共享引用。程序从绑定的源文、上一个候选和当前 CFG 生成可写范围。模型提交同一个 JSON 对象，每条记录和每个共享定义可以各占一行。完整且合法的旧格式也可以使用。Task 的源文隔离和七阶段调用预算保持原有设置。

## 记录如何被选用

程序从完整答复中分出有明确边界的记录，再检查授权、共享定义、操作坐标和依赖。能由唯一结构符号修复的错误会留下字符位置与摘要。缺少的语义、字段依赖和证据仍须通过原有编译器的校验。两项相互依赖的 CFG 更新会一起验证。局部拒绝、仍可使用的旧记录及真正采用的修改可以从阶段收据区分，原答保存在调用记录中。

普通保留不会自行消除语义异议。对于继续使用的已审查记录，程序可以把同一操作的契约义务、源码引用和消费者交给负责的阶段。复审重新对选中材料的义务给出结论。验证失败的记录和已受 CFG 改动影响的记录需要重新建立有效语义。

以归档的 `ir_617` 为例，源码先调用 `sanitizeFilename(operation)`，再用返回值筛选文件。CFG 只登记了筛选。上轮 CFG 修订有权调整这条 IR，但在受保护的约束数组里追加了一句输出说明，整个槽被拒绝。随后的 processing 修订提交了两项动作，跟仍然生效的单项清单不一致。补上 JSON 括号后，这个问题才独立显现。

离线对照使用同一个获授权的 CFG 槽，保留原块、控制边和约束，在原块登记两个动作。processing 引用这两个动作，将调用、局部字符串值和过滤结果接起来。按槽修订接受了这个改动，完整 CFG 通过 Lean，整份 processing 通过正式校验。归档的六块方案仅移除追加的约束仍有一处源文定位越界。历史运行保留原记录。[对照与诊断](../../output/verification/scoped-revision-20261124/ir617-witness.json)

## 调用、响应与包装函数

在源码足以证明绑定关系时，程序将一次调用的接收方、实参和响应配对，再将数组或对象解构作为本地字段操作。例如普通 GA4 报表用的是 SDK 返回元组的第一个成员。包装函数进入共享函数体时，通过实际实参、前驱和返回消费者建立关系。两个源码调用即使名称和实参相同，仍可有各自的调用身份。复杂表达式沿用原有语义校验和修订路径。

## 哪些字段受审查发现影响

修订位置说明可以编辑哪里。需求计算使用具体操作、调用配对、输入槽、字段和信息属性判断影响。模型可以在有源码依据时使用可选的 `affected_ranges` 表达更细的范围。该项复用已有的操作位置和字段选择器，普通答复无需填写。程序生成的入口来源缺口依其真实获取位置与传播记录判断影响。不同接收方或仅在默认分支读取的值会分别处理。

源文审查先汇合模型发现与程序派生发现，再核对已接受的契约。DOE 重建凭据时使用同一判断。无参 helper 的调用接口可被确认，同时保留其内部响应的未绑定来源。只有受争议的范围及依赖它的结果失去删除依据，独立字段仍可得到保留或删除结论。旧产物由对应版本的只读路径验证。
