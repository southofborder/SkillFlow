## 反向需求的起点怎样得到

起点不是“这条 IR 目前拿了哪些输入”，也不是从已经暴露的载荷倒推任务需要。
现有七调用流程先只从完整冻结 Skill 提取并封存 Task；Task 保存声明的目的、要求、问题及原文依据，
不接收 CFG、processing、敏感性或 DOE。随后 task correspondence 把这些要求对应到实际履约的结果、
动作、交付或条件位置，声明六类正向需求及路径；末尾的源文审查核对这些对应。
程序从这些明确的目标向前追溯生产关系，在数据流上进行反向需求计算。

因此可以细到字段，但精度需要具体依据。例如要求“返回客户姓名”，可以在实际返回值的
`["name"]` 建立 `value` 需求，而不是因为实现读取了整份客户记录，就把整份记录当作需求。
如果任务明确要求整个结果，起点仍然保持整个结果。存在性、数量、结构、条件真值和动作分别用
`presence`、`cardinality`、`shape`、`truth`、`action` 表达，不能都解释成需要原始明文。
源文不明确或映射缺失时必须留下具体缺口，不能凭字段恰好存在就生成精确任务要求。

导师指出“不显然”的地方成立：有字段路径，并不能自动证明黑箱计算只需要这些字段。
本轮新增的正是这层语义依据及其审查，而不是单纯在结果中增加“是否必要”的布尔字段。

## 黑箱计算怎样排除多写的输入

对已支持的选取、构造、更新和受限表达式，程序继续使用明确传递规则。
对其余计算，processing 从源文声明 `compute.demand_transfer`，描述“保持某个输出信息，需要哪些输入信息”。
processing 不读取 Task 或后续需求，因此不能为了得到更小的需求集合而倒推依赖契约。

例如 `y` 的 IR 声明输入 `a`、`b`、`c`，源文语义实际上只需要 `a.a` 和 `b.b`：

| 实际输入 | 必须保留的范围 | 其余信息 |
| --- | --- | --- |
| `a` | `value`，路径 `["a"]` | 对该输出独立 |
| `b` | `value`，路径 `["b"]` | 对该输出独立 |
| `c` | 空列表 | 对该输出独立 |

每条输出规则必须逐一交代所有实际输入，不能通过漏写 `c` 来宣称它无关。
源文审查接受后，`y` 的需求只反推到上述两个字段。若 `c` 没有其他任务需求、消费者或适用约束需要保留，
该输入使用可直接判为 `deletable`，不是只给出待考虑的候选。
此处的独立性相对于指定输出；`c` 仍可能被另一个输出或消费者需要。

每个输入行同时声明 `required` 和 `remainder`。`remainder=independent` 明确覆盖所列需求之外的部分；
`remainder=unresolved` 则必须提供具体的缺失事实、原因和源文证据。
“这是黑箱”“计算不透明”本身不够，必须说明缺的是哪段实现、哪个接口条件或哪种目前无法处理的关系。

输出规则按“信息属性＋路径”精确匹配，不能把整值规则当作任意子字段的精确规则。
对于复合输出，可以显式提供 `output_parts`，声明这些部分连同必要结构完整覆盖输出；
每一部分都必须有对应规则，并由源文审查核对完整性。仅列出若干子字段规则不代表已经覆盖整体。
无法匹配的输出或部件内部排除会留下定位清楚的未决原因。

## 工具调用的假设只覆盖接口必需字段

用户确认的假设是：有源文／接口依据的必需字段对履行工具接口足够且必要。
这不包括实际传入的所有额外字段。例如接口只需要 `record_id`，实际载荷却还带有 `internal_note`，
则前向事实继续保存二者，接口契约只保留有依据的必需字段；额外字段继续进入必要性和 DOE 判断。
不能因为参数已经被传给工具，就据此声明它必要。

对于源文明确规定“存在时才传递”的可选字段，输入要求可以标记 `if_present: true`，
保留存在性及存在时所需的信息；已经确定缺席时不误报缺少必需输入。默认 false 不输出，
输出选择器和 `output_parts` 不能使用此标记。某次载荷恰好缺少字段不能证明接口将其定义为可选，
仍必须由源文／接口依据及独立源文审查支持。

`call.input_contract` 会关联到请求和响应，程序检查配对一致性，并把它编译到独立的
`compiled_annotation.input_contracts` 表中。实际输入、可能观察和前向传播不会因此被删减。
这轮没有增加工具执行、额外模型阶段或最终 DOE 裁决调用。

## 谁审查，怎样避免自行证明

原有末尾源文审查得到完整源文、实际所选标注和完整契约清单，必须逐契约返回
`accepted`、`rejected` 或 `unresolved` 及证据。它既要检查“所列字段确实必要”，也要检查
“排除的部分确实独立”，还要检查复合输出分解与工具接口范围。
processing 自己写出的理由、有效行号或审查 findings 为空，都不能自动视为接受。
与该操作、其上级标注位置或所属 CFG 指令的已知缺陷冲突时，也不能同时接受契约。

拒绝或未决会交给 processing 负责，并使用既有共享修复轮次及依赖重建，不另开一次分析流程。
最终所选版本保存 `audit/input-contract-review.json`，绑定源码、CFG、Task、原始／编译标注、
映射和完整契约清单。正式 DOE 的保存、加载和零调用重放核对这份回执，不能换一版标注后沿用旧接受意见。

这些哈希和引用检查保证材料身份，不证明语义意见必然正确。语义可信度来自单独的源文审查及其具体证据，
不是自动形式化证明，也不意味着已经建立全局最小性或自然语言与程序的完全等价。

## 新的判断与边界

结果清单覆盖 IR 输入、具体操作输入以及 read／receive 的获取结果，保留索引、实际 Data、
版本、位置和覆盖状态。每个信息范围分别标记：

| 状态 | 含义 |
| --- | --- |
| `required` | 有非保守的任务保持推导要求保留。 |
| `deletable` | 已完成的需求分析不需要该范围，并且适用限制可以保持；这是当前分析前提下的可删除结论。 |
| `unresolved` | 具体的语义、审查、覆盖、任务要求或限制保持依据仍然缺失，不能判定。 |

尚未到达的节点只保留覆盖记录，不伪装成已经判定可删除。局部契约缺口沿实际推导链和受影响字段传播，
不会只因为共用一条 IR 就把无关字段全部变成未决。尚未表达的 Task 要求和 Task 问题仍按已有全局规则约束结论。
正向限制检查不创造需求、不删传播事实，发现已有违反也继续保留。

`input_findings` 区分多余输入、错误输入和缺失输入。错误／缺失输入需要已有 expected 关系或明确缺失需求等依据；
不能从变量名猜测作者真正想写哪个操作数，也不判断多取信息究竟出于误写还是有意为之。

敏感性分析可以引用已完成的输入判定，支持具体使用处的 `remove_input` 或 `exclude_field`。
所有 sink、接收方、条件、版本和敏感声明仍参与比较；可能影响仍不能当作敏感明文必然包含。
数组元素删除可能改变后续索引，因此不能仅凭字段式无需求自动生成元素删除方案。
获取结果无需求说明取得的信息没有任务用途，并不自动证明远端接口支持更窄的获取方式。
分析器不会实际改写或执行 Skill。

旧文档中的“没有需求不等于删除许可”应据此区分：**已经完成且有语义审查依据的反向需求分析后无需求，
可以支持删除；缺少分析或缺少任务依据，不等于已经证明无需求。**历史运行及其原有判定保持不变。
