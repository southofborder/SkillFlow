# Review recovery and dependency-local runtime failures

This change addresses three independent causes of incomplete analysis observed in
the closed GA4 processing restart. A `partial` result is not by itself evidence
that the runtime contract is too weak. Review delivery failures, a model's invalid
representation, unsupported source semantics and interpreter failures must remain
separate, located outcomes.

The review correction operates on a finite set of existing records and missing
obligation slots. The program derives those slots from the complete current
inventory, closes conflicts across affected findings and checks, and validates
the entire merged response. Unchanged prior answer records remain immutable on
disk; all source files, contracts and runtime vocabulary remain in the delivery.
Unknown or ambiguous correction scopes still require the full-response form.
This removes redundant delivery, not semantic material or validation.

If the existing correction request ends with a known delivery failure, usable
independent records from the complete first response can survive ordinary strict
local isolation. The retention receipt binds the original response, existing
normalization, validation, transport failure, material and isolation result.
Missing, invalid and conflicting scopes stay blocked. The report remains partial
and retains the actual request failure. Unknown process state and recording or
identity faults do not qualify. The existing shared repair consumes retained
findings using its existing dependency closure and budget.

Location identity now explicitly distinguishes unknown content from an unknown
address. `address_kind` defaults to `identified`; `unidentified` requires a
specific reason and physical source evidence, whose semantic adequacy is checked
by source review. Names are opaque labels. Unknown exception or argument values
do not alias other named slots merely because their contents are unavailable.
Genuinely unknown addresses retain conservative same-kind aliasing and weak
writes. Strict collection guards and immutable Data identities remain enforced.

Typed operand and collection-domain failures retain the IR, operation, input
Data and successful-prefix observations. Registry mutations from the failed IR
are rolled back. The solver marks declared outputs and possible writes as
unavailable and carries this through actual value, state, member and control
dependencies. Independent work continues. A later definite overwrite can release
a state dependency; control is released only at proven finite reconvergence.
Unexpected programming and integrity faults remain fatal. Work left unexecuted
after an abort is not proved infeasible and cannot justify deletion.

Runtime contract v12 gives the supported vocabulary a checked inventory: 14
atomic operations, the flat call form, three structural forms and 14 structured
expression operators. It specifies domains, identity and aliasing, effects,
failure and evidence requirements. Tests compare this inventory with the actual
schemas. This closes the specification over supported operations; it does not
promise to express every possible Skill or external tool behavior. Unsupported
semantics require a specific local gap. Tool interface necessity still requires
interface evidence rather than the current arguments alone.

New guided runs use v17, stage v14, annotation v11, flat annotation v6, fragments
v9 and source-review fragment v7. Compiled mappings use v15, runtime profiles
v24, propagation v22, demand v11, sensitivity review v9 and DOE v11. The Task
interface and its source-only responsibility are unchanged. Old artifacts retain
their original producer identities and conclusions.

The accepted-upstream import creates a separate new owner. It preserves complete
source, selected Task/flow/CFG and the accepted evidence chain under their original
identities, verifies their relationship, and binds the copies in a receipt. The
new run regenerates processing, task correspondence, sensitivity and source
review. Shared repair can rebuild later dependencies if needed. This preserves
the seven-stage policy with three inherited stages and four fresh normal requests,
two workers, one correction per stage, one shared repair round and existing
transport budgets. New cost excludes inherited calls.

Offline receipts and original failures are under
`output/verification/runtime-locality-20261117/`. The final acceptance receipt is
the authority for test counts and the frozen implementation. Online preparation
and the sole controller are under
`output/verification/online-ga4-runtime-locality-20261117/`. They must not run
before offline acceptance. The subsequent assessment must report actual review
coverage, propagation, source boundaries, input assessments, DOE and cost; an
online success is not asserted by this design document.
