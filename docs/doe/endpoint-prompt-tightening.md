# Endpoint demands, acquisition scope, and review evidence

This is an offline follow-up to the first-response screen. It changes teaching examples, shared prompt instructions, and review-stage mechanical diagnostics. It makes no model requests and does not rerun the three formal cases. Business schemas, the runtime contract, forward propagation, backward demand, and sensitivity rules remain unchanged.

## Preserved prompt organization

Both prompts keep seven sections: authority, input, format, workflow, rules, examples, and self-check. The annotation prompt teaches valid construction; the review prompt teaches how to locate a discrepancy and cite support. Fixed-Task repair and independent re-review reuse the corresponding production templates. Structural correction remains unlimited; semantic repair still uses one shared budget. The structural correction protocol remains v5.

## Required content belongs at the actual receiver

The independent calibration lesson acquires a whole packet, selects `badge`, `offset`, and a Boolean inclusion control, constructs a request, and delivers it. Its delivery has an action demand and two value demands on input slot 0, at paths `badge` and `offset`. The unconditional badge illustrates `expected` and `expected_path`. The conditional offset uses the already explicit original-value path through selection and build; membership uses the existing build `when` relation. A redundant expected source reference is omitted for that optional field.

This distinction is executable, not only stylistic. An expected source reference creates an independent preservation seed under current rules; it does not inherit the build guard. The offline false-condition check found that adding it to the optional offset conservatively retains the source field even when the member is omitted. Without that redundant expected reference, the false branch stops before any offset content is consumed, while the true branch reaches the original field through the supported operation path. The nominal boundary-path goal is still present, but it does not prove an absent member was exposed. This update uses existing rules and does not add conditional demand fields or change the solver.

A shape demand preserves structure, not required parameter values. An action demand preserves an action, not its payload. Upstream construction demands do not automatically become receiver demands. Independent requirements on construction or returned values remain valid; duplicate seeds are not required merely to repeat an already supported relationship.

The controlled contrast changes only demands. It places content seeds on build inputs, leaves action and shape at delivery, and adds an unsupported whole-value seed at acquisition. The request itself is unchanged and correctly constructed. Both candidates are structurally legal. The missing receiver demands and excessive acquisition demand are semantic issues, not errors the schema can infer from source text.

Each recipient, repeated call, and applicable terminal remains distinct. A write must preserve specified behavior and the current write payload; an append does not make the old file content a task requirement.

## Acquisition is not task demand

Acquisition and observation describe what is obtained or may become visible. Task demand describes what must be preserved under the declared task and supported analysis rules. A whole read does not by itself justify a root value seed. Conversely, narrow demands do not change the actual read or observation.

Explicit whole-object obligations, ordinary returns, real Boolean results, counts, pure action requirements, and conservative opaque dependencies remain valid. Conservative request retention through a receive is not a substitute for precise required parameters. Model-side processing demands still reach the relevant model entrance; a narrow downstream delivery cannot erase them.

## Review locations and evidence are different reference spaces

| Field | Refers to | Purpose |
|---|---|---|
| `findings[].target_ids` | Supplied review targets | Locate a sealed Task claim, candidate claim, generated observation, or existing parent for an omission. |
| `goal_checks[].raw_pointer` | Exact supplied goal-index strings | Check existing seeds; an absent seed has no pointer. |
| `evidences[].target` | Real CFG objects | Support graph operands, constraints, or metadata. |
| Source span or `rule_id` evidence | Frozen source or runtime rules | Support a requirement, mechanism, or applicable default. |

An annotation processing segment or atomic operation is not a CFG path. A finding target already locates the candidate demand list. CFG evidence supports only the real graph fact it cites; it cannot prove what demands the candidate contains. Sufficient source-only evidence is allowed. Actual CFG metadata named `events` remains valid: resolution uses the real object, not a field-name blacklist.

The full review lesson contains four-axis coverage and two annotation-domain findings. The excessive existing read seed is flagged in goal checks. The missing delivery seed is reported through the requirement check and an existing delivery parent, without inventing a goal pointer. Other legitimate seeds remain accepted.

## Complete examples and targeted diagnostics

Tests extract examples from the actual rendered requests, validate all provided context and required fields, compile annotations, and validate review responses. The full review target table uses the same compact ID-to-pointer projection as the actual model input; internal bookkeeping is not copied into the teaching prompt.

Review evidence validation preserves typed errors and precise child paths such as `/findings/0/evidences/0/target`. Context contains the current target, schema-derived allowed forms, and one relevant namespace example. Multiple independent bad CFG citations share that short example. File, line, runtime-rule, and coverage errors do not receive an unrelated CFG hint. The failure branch uses the same evidence validation.

Raw diagnostics remain in audit records. The program does not add `path`, translate references, move evidence, delete findings, or create demands. Unexpected implementation exceptions do not become correction requests. A valid `cannot_assess` remains a terminal semantic failure under the existing policy.

## Acceptance boundary

Offline acceptance checks executable examples, actual sink demand derivations and seed identities, conditional membership, whole-read preservation, receiver isolation, write payloads, typed diagnostics, fixed-Task repair routing, response preservation, interruption/resume, and zero-API replay. Multilingual genuine input coverage remains.

Prompt character and UTF-8 byte changes are reported on identical frozen inputs. Complete examples can increase request size. Offline tests do not measure a reduction in model structural-correction frequency, token costs, or semantic errors. Any future online validation has a separately agreed scope and budget.
