# Prospective formal CLI candidate

This module is an **offline implementation candidate**. Implementing it, importing
it, passing its synthetic tests, or reading this document does not authorize an
experiment. The paused CLI-v3 calibration remains paused. Its locks, unanswered
request and unknown usage remain evidence. No actual formal workspace, protocol
adoption, human approval, gate or request was created during this continuation.

`formal_cli.py` is separate from the calibration-only `cli_amendment_v3.py`.
Nothing here changes that older module's permanent ban on formal dispatch. The
new candidate preserves the frozen comparison's 24 selected cases, six reserves,
216 main workflows, 48 fixed direct reviews, three repeats, scoring rules,
independence requirements and statistical thresholds. Source/prompt/reference
identity mismatches stop preparation and dispatch. Entry-root reachability and
the eight-operative-file count remain distinct under the existing selection
rules.

## Closed prerequisites

`inspect_readiness(...)` is read-only and returns zero-call diagnostics. A future
formal preparation would require all of the following existing evidence:

- Exact long preparation, ordered selection, complete source packets, rules,
  templates, rendered prompts, fixed schedule and human assignments. Current
  selection must also be replayed by the current frozen selector through the
  separate reference epoch's `current_selection_binding`; an older byte seal is
  insufficient to establish present eligibility.
- All 30 complete source-only semantic references, a separately imported actual
  human roster, and 60 current-version personal confirmations from two distinct
  registered reference verifiers per case. The separate reference epoch binds
  the exact source tree, bundle, reference revisions and imported confirmations.
- All three finished native CLI-v3 engineering calibrations for `gh-fix-ci`,
  `netlify-deploy` and `transcribe`, complete candidate seals, conformant receipts,
  known response usage, and passed native/request replay bound to saved bytes.
  Paused, stopped or locked calibration state fails immediately. A saved
  `passed` flag or calibration authorization alone cannot satisfy this gate.
- The identical production implementation and unchanged pinned CLI-v3 adapter,
  model, effort, provider, executable, argv and observed runtime harness.
- A separate formal-specific proposal and actual explicit user adoption binding
  every final material, reference, implementation and calibration identity. The
  software validates existing records and does not manufacture consent or
  personhood evidence.

These conditions are presently unmet. In particular, offline validation does not
authorize resumed calibration or reclassify a historical source seal as current
source eligibility. Current source review failures require evidence resolution
under the frozen rules; no automatic replacement or rule relaxation exists.

## Future execution interface

The candidate exposes `prepare_formal_run`, `verify_formal_gate`,
`run_planned_workflow`, `dispatch_next_once`, `replay_formal`, `close_outputs`,
`build_cost_ledger` and `report`. The module can be inspected with
`python -m tools.doe.real_comparison.formal_cli --help`. This document intentionally
does not provide an experiment dispatch command.

The worker uses the unchanged `execution._native_pipeline` for SkillFlow, with a
fresh graph and injected CLI client for every repeat. Every semantic request uses
the exact production core prompt inside `execution.ENVELOPE`. The two direct
methods retain their own frozen prompts and output formats. A fixed review sees
the exact original source-only task and its same-case, same-method R1 answer.
Missing R1 produces `not_reviewable`; no R2 answer, substitute, score, reference,
other method output or reviewer advice is inserted.

Only `dispatch_next_once` may start a target process, after repeated full gate
and exact queued-material checks. It services one request, records a distinct
dispatch attempt, and calls the unchanged pinned CLI adapter. The process receives
the full UTF-8 material on stdin and a fresh empty working directory. Receipts
must prove the runtime, one final answer, no tools or delegation, exact visible
input, unique session/response identities and known per-response usage. This is
observed input/activity isolation; it is not proof of a hard filesystem sandbox.

The existing per-workflow limits remain 64 actual CLI processes, 8,000,000
reported tokens, six hours, 45 minutes per outstanding request and 300,000
delivered reference tokens. No clipping, implicit adapter retry, manual semantic
repair, semantic cache, automatic resume or final uncounted model polish exists.
Failed or unaccountable actual requests retain their evidence and close further
dispatch. The adapter supervises and terminates its own timed-out process.

## Replay, closure and accounting

Replay verifies exact prompt/envelope, launch/configuration pins, process and
stdout bindings, allowlisted raw receipt facts, visible answer and candidate
seals. Native stage replay uses saved calls without a model/network client.
Replay does not repair or replace a failed target answer. Closed outputs retain
all 264 planned outcomes, including technical failures, missing originals and
unattempted workflows terminalized after a global stop. Active workflows,
outstanding requests and actual processes without terminal supervision evidence
prevent closure. An output freeze permanently prevents further generation.
Workers observing a retained global stop terminalize only their own unlaunched
queued requests. In-flight processes remain outstanding until their actual
supervisor records a terminal outcome; no process result is synthesized.

`formal_cli_metrics.py` counts queued requests, attempted dispatches, proven
process starts, attributed responses and accepted answers separately. A dispatch
record alone never establishes an actual CLI process. Proven zero-process
prelaunch failures consume zero target tokens; a started process with missing or
conflicting response usage keeps unknown totals. An attempted dispatch with
unknown process-start evidence also retains unknown usage until a proven
prelaunch outcome exists. Identical response IDs are
deduplicated, and reuse still forbids another dispatch. Reasoning and cache
details are not added again to reported token totals. Queue wait, process
supervision, response time, local work and workflow elapsed time stay distinct.

Formal target, calibration, earlier/probe, preparation and human costs remain
separate. Enhanced direct methods include both the original R1 and fixed review
cost. The report routes closed and replay-verified candidates through the
unchanged human scoring, secondary-review sampling, paired source-cluster
statistics and symmetric efficiency contracts. Missing human checks or unresolved
judgments prevent a method-advantage conclusion. Engineering completion,
integrity replay and reference quotations do not establish semantic completeness
or absence of DOE.

An activated reference correction routes scoring and efficiency to the current
grading epoch. Target cost remains attached to the original frozen cohort;
current human work and deduplicated grading-epoch history are reported separately.
Copied target receipts in a grading workspace never create another target charge.

## Offline validation

The new focused tests use temporary fictional material and forbid real Popen.
They cover closed real interrupted state, old calibration authorization,
incomplete/current-version references, source/prompt/runtime drift, exact fixed
reviews, fresh native repeats, over-limit delivery, launch counters, unknown
usage, budgets and all-264 closure. Existing CLI-v3 adapter tests provide the
synthetic receipt checks for tools, configuration drift, duplicate final output,
exact stdin, timeout termination and no retry. The continuation diagnostics record
the actual executed test results separately; test counts are not semantic
evaluation evidence.
